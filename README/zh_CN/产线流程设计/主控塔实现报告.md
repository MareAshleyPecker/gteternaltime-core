## 2. 结构、容量

### 结构（3×3 底面积，塔身往上长 1~10 段）

```
   y = N+1  ┌───┐  顶盖：3×3 实心机壳
            │XXX│
            │XXX│
            │XXX│
   y = 1..N ┌───┐  塔身段（可重复 1~10 次）：
            │TXX│   3×3 环 = 8 格，中心是空腔
            │X X│   T = 段锚点（和 X 认同一批方块）
            │XXX│
   y = 0    ┌───┐  基座：3×3 实心，控制器嵌在一侧墙里
            │XXX│
            │XXX│
            │XSX│  ← S = 控制器
            └───┘
```

注册代码：`ETMasterTower.kt:117-140`（`FactoryBlockPattern.start(LEFT, FRONT, UP)`，`.setRepeatable(1, MAX_SEGMENTS)`）。

各格谓词：

| 符号 | 谓词 | 位置 |
|---|---|---|
| `S` | `Predicates.controller(Predicates.blocks(definition.block))` | 基座一侧墙的中心 |
| `X` | 机壳 `GTBlocks.CASING_STEEL_SOLID`（**至少 16 格**）`.or(Predicates.abilities(PartAbility.INPUT_ENERGY).setMinGlobalLimited(1).setMaxGlobalLimited(4))` | 基座 / 塔身环 / 顶盖 |
| `T` | 段锚点：**机壳或 GTM 能源仓**（与 `X` 同一批方块），额外往结构上下文 +1 段 | 每段一个固定角位 |
| ` ` | `Predicates.air()` | 每段环的中心空腔 |

「段数」怎么来的：`ETMasterTower.kt:179-189` 的 `segmentAnchor` 是一个 `Predicates.custom` 谓词，匹配成功就
`state.matchContext.increment(MasterTowerMachine.SEGMENT_KEY, 1)`；成型时 `MasterTowerMachine.kt:160` 用
`multiblockState.matchContext.getInt(...)` 读回。上下文由 GTM 每次结构检测开始时 `clean()` 清空
（`MultiblockState#clean` → `matchContext.reset()`），不会跨检测累积。

> 这套写法抄的是 GTM 自己的电池计数：`Predicates#powerSubstationBatteries`（`Predicates.java:270-293`）
> + `PowerSubstationMachine.BatteryMatchWrapper`。锚点认的方块和 `X` 完全一样，所以**玩家看不出区别**，
> 能源仓插在哪一格也不影响段数。

### 容量

```
容量 = 段数 × GTETConfig.towerSegmentCapacity()
```

- **每段容量当前 = 1,000,000 TF —— 这是占位值，待用户定稿**（`GTETConfig.DEFAULT_TOWER_SEGMENT_CAPACITY`，
  Java 注释里逐字标了「⚠️ 默认值 1,000,000 是**占位值**，等最终平衡数值定稿后再改这里」）。
- 段数上限 = 结构常量 `MAX_SEGMENTS = 10`（`ETMasterTower.kt:64`）；配置 `towerMaxSegments` 只负责把
  **计入容量的段数**往下夹（`MasterTowerMachine.kt:161`），因为图案是编译期常量、运行期改不了。
- ⇒ 占位期的容量上限 = `10 × 1,000,000 = 10,000,000 TF`（= `819.2 亿 EU`）。
- 存储用 long（整数 TF），没有亚 TF 精度（设定 §3 已定）。

## 3. 唯一性怎么实现的

**两套数据，两条线程**（`MasterTowerRegistry.kt` 顶部 KDoc 有对照表）：

| 数据 | 存在哪 | 谁能读写 |
|---|---|---|
| `MasterTowerRegistry.snapshot`（`@Volatile`，不可变 `data class Snapshot`，`MasterTowerRegistry.kt:54-67`） | 进程内存 | **任意线程只读**；`checkPattern` 只读它 |
| `MasterTowerSavedData`（`MasterTowerRegistry.kt:151-198`，键 `gtetcore_master_tower`） | 主世界 `DataStorage`（存档） | **只在服务端线程**读写 |

- 内存快照是**整体替换**的不可变对象（`snapshot = Snapshot(...)`），后台线程读到的要么是旧值要么是新值。
- `ensureLoaded(server)`（`:82-88`）把存档读进内存，触发点：`MasterTowerEvents.onServerStarted`
  （服务器起来时）**以及**塔侧每个写入口（成型 / 拆控制器）—— 后者是保底，事件没挂上也不会坏。
- **`checkPattern()` 里只读了一行**：`MasterTowerMachine.kt:217`

```kotlin
if (!MasterTowerRegistry.snapshot().allows(selfPos(lvl))) { deniedByUniqueness = true; return false }
```

  —— 无 I/O、无 `SavedData`、无 level 查询（只取维度拼一个 key）。

### 「已成型不拆」写在哪一行

**`MasterTowerMachine.kt:211`**，`checkPattern()` 的第一行：

```kotlin
if (formed) return super.checkPattern()
```

`formed` 是本类自己维护的布尔（`MasterTowerMachine.kt:75-83`），在 `onStructureFormed` 置真、
`onStructureInvalid` / `onMachineRemoved` 置假。它存在的唯一理由就是这条：GTM 在**已成型**状态下重检失败会走
`onStructureInvalid()` 把塔拆掉（`MultiblockControllerMachine.java:228-249`），所以唯一性门必须排在它后面。

### 语义（设定 §6.1）

- `Snapshot.allows(pos)`（`:57-58`）：`曾成型过 → 放行`；否则 `uniqueTower == null → 放行`；否则**拒**。
- **不追溯**：坐标一旦进过 `formedTowers` 就永远放行 —— 这同时解决了「`false → true` 配置翻转不波及老塔」
  和「重启后老塔要能重新成型」（`isFormed` 不落盘，重启后所有塔都要重新过 `checkPattern`）。
- `uniqueTower` 由**首座**占位，**只在控制器方块被拆掉时释放**（`IMachineLife#onMachineRemoved`
  → `onTowerControllerRemoved`，`MasterTowerMachine.kt:184-191`）。敲一格机壳（结构失效但控制器还在）
  **不释放** —— 否则「拆一格再补上」的空窗里别处就能抢建第二座。
- `masterTowerUnique = false` 时整道门直接短路（`MasterTowerMachine.kt:212-215`），每座塔各自独立记账。

### 「提示」落在哪

设定要「第二座不成型**并提示**」。实情：`checkPattern()` 跑在后台线程，不能发聊天消息；而 GTM 7.5.3 里
`PatternStringError#getErrorInfo()` **没有任何调用点**（本仓 `data/lang/Lang.kt:21-26` 已核实），
所以设 `worldState` 的错误串也没人渲染。因此提示做在**控制器面板**里：
`MasterTowerMachine.kt:328-331`，未成型且 `deniedByUniqueness` 时加一行红字
（键 `gtetcore.machine.master_tower.duplicate`，中英都有）。玩家右键控制器即可看到。

## 4. 换汇那一 tick 的代码路径

`MasterTowerMachine.exchangeTick()`（`MasterTowerMachine.kt:242-261`），由
`ConditionalSubscriptionHandler`（`:95-96`）订阅，**只在成型时订阅**，未成型自动退订。

| 步 | 代码 | 说明 |
|---|---|---|
| 1 | `if (!formed \|\| !isWorkingEnabled) return` | 未成型 / 软锤暂停都不换汇 |
| 2 | `val room = getTimeFlowRoom(); if (room <= 0L) return` | **容量满了就一点电都不取** —— 不白吞玩家的电 |
| 3 | `val container = energyContainer ?: return` | **取电的容器 = 塔自己聚合出来的那个**：`WorkableElectricMultiblockMachine#onStructureFormed` 里 `energyContainer = getEnergyContainer()`（`WorkableElectricMultiblockMachine.java:76-80`），内容就是玩家插在塔上的 GTM 能源仓的 `EnergyContainerList` |
| 4 | `val eu = container.energyStored` | 聚合容器的存量 |
| 5 | `val tf = minOf(ETTimeFlow.euToTf(eu), room)` | `euToTf` **向下取整**（`ETTimeFlow.kt:69`），再用剩余容量夹一次 |
| 6 | `val consumed = -container.changeEnergy(-ETTimeFlow.tfToEu(tf))` | **先算 TF 再反算 EU** 去扣 ⇒ 永远不会「扣了不足 1 TF 的电」；零头原样留在能源仓，下一 tick 继续攒 |
| 7 | `setTimeFlow(stored + ETTimeFlow.euToTf(consumed))` | 按实际扣到的电折回 TF 入账 |

- 充入效率 **η₁ = 100%（无损）**，与任务要求一致；**潮汐不参与充入**，只在面板里显示（设定 §3.1 的
  「换算只在主控塔里发生」指的是塔是唯一闸口，不是"充入要乘潮汐"）。
- `setTimeFlow` 的上限取 **`max(capacity, stored)`**（`MasterTowerMachine.kt:114`）而不是裸 capacity：
  塔重建后段数变少时，超出部分的储备不会被第一笔取出悄悄销毁（`getTimeFlowRoom` 自然变 0，只能出不能进）。
  ⚠️ 这一条**故意偏离**了 `ITimeFlowStorage` 注释里「必须夹到 `0..getTimeFlowCapacity()`」的字面要求，
  理由写在方法 KDoc 上；正常充入/取出路径行为与契约一致。

## 5. 封存方案：为什么选「封存进控制器（塔芯）的掉落物」

**方案**：塔芯 = **控制器方块本身**（它是结构必需品）。走 GTM 现成的 `IDropSaveMachine` 通道：

- 敲掉控制器 → `MetaMachineBlock#getDrops`（`MetaMachineBlock.java:229-248`）→ `saveToItem(drop.getOrCreateTag())`
  → `saveManagedPersistentData(tag, true)` → `MasterTowerMachine.saveCustomPersistedData(tag, forDrop=true)`
  （`MasterTowerMachine.kt:271-275`）把储备写进掉落物 NBT；
- 再放下控制器 → `MetaMachineBlock#setPlacedBy`（`:113-134`）→ `loadFromItem(tag)` → `loadCustomPersistedData`
  （`MasterTowerMachine.kt:281-287`）还回塔里；那一刻结构还没成型（容量 = 0），所以**直接给字段赋值**、不走
  `setTimeFlow`（否则会被夹成 0）。
- 掉落物 tooltip 会显示「封存储备：N TF（= M EU）」（`ETMasterTower.kt:143-155`）。

**为什么选它**：

1. **它就是"塔芯"**：控制器是结构必需品，塔一拆就必定掉出来，不用再造一种新方块 / 新物品；
2. **零新机制**：`IDropSaveMachine` + `saveCustomPersistedData(tag, forDrop)` 是 GTM 自己给
   `PowerSubstationMachine` 用的同一条路（PSS 的储能就是这么过掉落物的），javap 已核实
   `IAutoPersistBlockEntity.saveManagedPersistentData` 的字节码结尾确实回调
   `saveCustomPersistedData`，`loadManagedPersistentData` 结尾回调 `loadCustomPersistedData`；
3. **不与「拆一半再建」打架**（任务让我判断的那条）：只有**控制器被敲掉**才走掉落物通道；
   敲的是机壳 / 能源仓时控制器方块还在，储备一直躺在控制器自己的存档数据里，什么都没动。
   控制器没被敲掉时唯一的性名额也不释放，所以也堵住了「拆一格抢建第二座」。

**没有默默改语义**：设定 §6.1 原文是「拆塔时把储备封存成物品」——本实现**就是**封存进物品（控制器的掉落物），
不是替代方案。真正的边界只有一条，如实写在这里：**重建后的容量比原来小**（例如只接 2 段、原来存了 5 段的量）
时**不销毁超出部分**，玩家可以慢慢取走（见第 4 节最后一条）。

## 6. 瓶子绑定手势改成了什么

**改动文件**：`src/main/kotlin/rain/gtetcore/gtet/common/item/timeflow/TimeBottleBehavior.kt`

| 行 | 内容 |
|---|---|
| `:123-124` | `override fun onItemUseFirst(itemStack, context)` → `towerGesture(context)`（**主入口**） |
| `:133` | `override fun useOn(context)` → `towerGesture(context)`（等价备用入口） |
| `:136-159` | `towerGesture`：手里必须是瓶子 → `TimeFlowTowers.find(level, context.clickedPos)` 找塔 → 找不到就 `PASS`；非潜行 = **绑定**（`TimeBottleData.bindTower`），潜行 = **解绑**（`TimeBottleData.unbindTower`） |

### 为什么手势写在 `onItemUseFirst` 而不是只用 `useOn`

任务原文是「给瓶子自己的交互链加 `useOn`」。**只加 `useOn` 不管用**，证据是 Forge 对
`ServerPlayerGameMode#useItemOn` 的补丁（`forge-1.20.1-47.4.23-sources.jar` 里
`patches/net/minecraft/server/level/ServerPlayerGameMode.java.patch`），顺序是：

```java
UseOnContext useoncontext = new UseOnContext(p_9266_, p_9269_, p_9270_);
if (event.getUseItem() != DENY) {
    InteractionResult result = p_9268_.onItemUseFirst(useoncontext);   // ① 最先，非 PASS 直接 return
    if (result != InteractionResult.PASS) return result;
}
boolean flag1 = (sneaking && holding) && !(...doesSneakBypassUse...);
if (...) { blockstate.m_60664_(p_9267_, p_9266_, p_9269_, p_9270_); }   // ② 方块自己的 use
...
interactionresult1 = p_9268_.m_41692_(useoncontext);                     // ③ ItemStack#useOn
```

而主控塔是 GTM 控制器：`MetaMachineBlock#use`（`MetaMachineBlock.java:317-320`）在**没潜行**时会
`tryToOpenUI(...)` 把右键吃掉并返回，于是第 ③ 步**永远不会被调到** —— 这就是「手持瓶子右键塔没反应」的根因。
把手势放到第 ① 步就绕开了它。`useOn` 保留成**等价实现**（顺序万一被别的 mod 改了、或将来塔不是 GTM 方块时仍成立）。

**副作用（如实说）**：两种手势都会吃掉这次右键 ⇒ **手持瓶子时打不开塔的面板**，换空手右键即可。
绑定比开面板常用，且与闪存的既有手感一致，所以这样定。

**手感决策**：非潜行 = 绑定、潜行 = 解绑（与 GTM 闪存的 `onDataStickUse` / `onDataStickShiftUse` 同构），
按任务给的第一方案实现，没有自创。

**找不到塔**：返回 `PASS`，什么都不做（右键交还给方块本身）—— 不给错误提示，免得玩家在自家墙上右键一下就弹红字。

**没权限也照绑**：`canUseTimeFlow` 是"能不能取用"，与"绑在哪"是两件事；没权限时给一条
`item.gtetcore.time_bottle.tip.bound_denied` 提示，说明扣费会回落到瓶内 TF。真正拦截在
`TimeBottleData.tryPay`（已存在的代码，`TimeBottleData.kt:265` 里就调了 `tower.canUseTimeFlow(player)`）。

### 闪存那条路留着会不会有冲突

**不会冲突，但它今天也不会触发。** 塔机器额外实现了 `IDataStickInteractable` 并把回调转发给
`TimeBottleData.onDataStickUse` / `onDataStickShiftUse`（`MasterTowerMachine.kt:304-313`），
但那两个方法的第一句是 `if (!isTimeBottle(stack)) return PASS`，而 GTM 的 `DataItemBehavior`
分发进来的是**手里那根闪存本体**（不是瓶子）⇒ 恒 `PASS`，GTM 继续走它原来的流程，闪存行为**一字未变**。
换句话说：留着它只是不给将来留坑（将来若有"瓶子形状的闪存"或别的分发入口，这条路是通的），
瓶子的真实入口就是第 6 节那两条。

## 8. 没验成 / 存疑的点

**一次游戏都没跑过** —— 下面全部只有静态证据。

1. **塔容量占位值**：`1,000,000 TF/段`、上限 `10 段` 都是**占位**，待用户定稿。代码注释与本文都已标明，
   改一处即可（`GTETConfig.DEFAULT_TOWER_SEGMENT_CAPACITY`）。
2. **结构能不能真的成型**：图案（`LEFT, FRONT, UP` 三轴 + 可重复段 + 段锚点计数）**未实机验证**。
   风险点：① 可重复段的起点/终点判定（抄的 PSS 写法，但 PSS 的控制器在第 0 层、本塔也是，理论上一致）；
   ② 段锚点谓词在 JEI 预览 / `autoBuild`（结构工具自动搭建）里的表现未验。
   卡在哪：需要跑 client 摆一遍。**若成型失败，第一个要看的是 `.aisle` 的行列方向**。
3. **`MasterTowerEvents` 有没有被 Forge 注册**：`@Mod.EventBusSubscriber` 写在 Kotlin 类的
   `companion object` 的 `@JvmStatic` 方法上（本仓先例 `TerminalGroupSeeder` 是 Java 类）。
   即使没注册也不会坏 —— `ensureLoaded` 在塔侧每个写入口都会兜底。**未确认它是否真的被调**。
4. **白名单够不够用**：现在只有「所有者 + 配置里一份**全局**逗号分隔 UUID 串」
   （`towerWhitelist`），**没有按塔分别维护的白名单、也没有游戏内编辑入口**（设定 §6.1 说「可配置/可编辑」，
   这里只做到了「可配置」）。多人服若要求「每座塔一份名单」，需要再加 UI 或命令。
5. **封存语义的两条边界**：
   - 重建后容量变小 ⇒ 超出部分**不销毁**（刻意的，见第 4/5 节），但**未实机验证**取出是否顺畅；
   - `forDrop` 之外的路径（区块正常存档）也写同一个键，理论上不与掉落物互斥，但**未实机验证**
     「拆塔 → 掉落物带 NBT → 重新放下 → 数值还原」这一整条链。
6. **唯一性的并发窗口**：`snapshot` 是懒加载的，服务器刚起来、存档还没读进内存的那几秒里，
   理论上新塔可能抢先成型（`MasterTowerEvents.onServerStarted` 就是为关掉这个窗口加的，
   但见第 3 条未确认）。实际影响：最多多出一座塔，且它会被记进 `formedTowers` 永久放行。
7. **「已成型过就永久放行」的代价**（诚实标注）：把旧塔拆掉后原地重建、同时又在别处建了新塔，
   两座都会工作。这是「配置翻转不追溯」这条需求的必然代价 —— 门只挡「从未成型过的新塔」。
8. **面板上的「重复提示」是不是足够显眼**：只有右键控制器才看得到，**没有聊天消息**（后台线程发不了）。
9. **`onItemUseFirst` 手势**：顺序依据来自 Forge 的补丁源码（证据充分），但**实机手感未验**；
   尤其是「手持瓶子时打不开塔面板」这条副作用需要用户确认可接受。
10. **潮汐不参与充入**：这是按任务「充入效率 η₁ = 100%，即无损」做的；设定 §3.2 的潮汐在充入侧
    目前只做显示。若用户要潮汐影响换汇，需要在 `exchangeTick` 第 5 步乘 `tideRate`（**未实现，等指示**）。
