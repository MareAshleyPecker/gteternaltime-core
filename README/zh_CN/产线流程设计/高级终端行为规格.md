# 高级终端行为规格（净室实现用）

> **这份文档的用途**：让一个从未见过 GTMT 高级终端源码的人，能照着它写出一个**功能对齐**的新终端。
> 文档只写「做什么、在哪、取什么值、什么条件下」，不写「怎么写」——所有方法都以**调用契约**（类名 + 签名）出现，
> 具体实现由实现方自己决定。
>
> **背景**：本仓原本把 GTMThings(GTMT) 的物品「高级终端」打补丁来用；由于 GTMT 的授权状态存疑（CurseForge 显示 ARR、
> 仓库无 LICENSE 文件），决定剔除 GTMT、自建一个新终端。为避免衍生作品，新实现**不得参考** GTMT 源码，
> 只能依据本文档 + 本仓已有的 `common/item/terminal/` 包（那部分是本仓自己的代码，可直接复用）。
> **2026-09-27 起 GTMT 已整体剔除**（补丁 jar、`modpatch/gtmthings-*`、`mixin/GTMT/` 三个 mixin、
> `util/LiveGlobalCountView`、`dev.tierSelectEnabled` 配置项全部删除），自建终端已落地，见 §8.2。
>
> **术语约定**：下文「终端」指要新建的这个物品；「控制器」指 GTM 的 `IMultiController`（多方块主机）；
> 「结构 / 图案」指 GTCEu 的 `BlockPattern`；「分级组 / 组」指一组可互相替换的候选方块（例如各等级线圈）。
> 「原实现」= 本仓原先使用的 GTMT 补丁版终端（**已剔除**），它的行为是本文档要对齐的目标；
> 下文提到「原实现的类/常量」均属历史信息，在仓库中已不存在。

## 1. 物品与交互

### 1.1 注册

| 项 | 值 |
|---|---|
| 物品 id | 新模组自己的命名空间（本仓 modid `gtetcore`）；原 GTMT 的 id 是 `gtmthings:advanced_terminal`，**不要沿用** `gtmthings` 命名空间 |
| 物品类 | GTCEu 的 `ComponentItem`（`com.gregtechceu.gtceu.api.item.ComponentItem`） |
| 挂载方式 | 通过 `GTItems.attach(IItemComponent...)` 在注册时挂上终端行为组件；该组件实现 GTCEu 的 `IItemUIFactory` |
| 堆叠上限 | 1 |
| 耐久 / 工具属性 | 无耐久；不属于任何 GTToolType（这一点必须保持：见 1.2 的潜行分支） |
| 创造模式标签页 | 原实现用 `GTRegistrate.defaultCreativeTab(null)` 注册，没有自己的标签页。新实现建议注册进本仓已有的「GTET 物品」标签页（`GTETCreativeModeTabs.ITEM`），或直接用本仓 `ETREGISTRATE` 的 `itemAndLang(...)` 辅助注册 |
| 获得途径 | 原实现是**工作台有序配方**：图案 3×3 为「S G S / P B P / P W P」，其中 S = 钢螺丝、G = `forge:glass_panes` 标签、B = 书（`minecraft:book`）、P = 钢板、W = 锡单线。新实现自定配方即可，建议保持相近成本 |
| 注册名 → 语言键 | `item.<modid>.advanced_terminal` |
| 贴图依赖 | ⚠️ 原实现的模型是 `item/generated` + 第一层贴图 `gtmthings:item/advanced_terminal`，该 PNG 是**逐帧动画**（配套 `.mcmeta` 里 `frametime = 6`）。GTMT 移除后这个命名空间不存在了，**新实现必须自备一张 16×16 贴图**（是否做动画自定），不得引用 `gtmthings:` 下的任何资源；模型与 lang 建议交给 Registrate 的数据生成产出（**已自备静态贴图 `assets/gtetcore/textures/item/advanced_terminal.png`**） |

### 1.2 交互

终端的交互被 GTCEu 的 `ComponentItem` 分发给挂在上面的组件；触发顺序受原版与 Forge 的右键规则约束。

| 动作 | 触发条件 | 服务端做什么 | 客户端做什么 | 返回 |
|---|---|---|---|---|
| 右键空气 | 任意（含潜行） | 走 `Item#use`，由 `IItemUIFactory` 的默认实现打开界面：调 `HeldItemUIFactory.INSTANCE.openUI(ServerPlayer, InteractionHand)` | 不发包，等界面同步 | 成功 |
| 右键方块（未潜行） | 方块自身不消耗交互 | 同上（原版在方块 `use` 返回「未消耗」后回落到物品的 `use`，客户端侧也会回落到 `use`，因此最终会打开界面） | 同上 | 成功 |
| 右键 GT 机器方块（未潜行） | — | 机器方块自己的 `use` 会打开**机器自身**的界面并消耗交互，终端界面不会打开 | — | 与终端无关 |
| **潜行 + 右键方块** | 主手是终端（非工具、`doesSneakBypassUse` 为 false，所以原版会**跳过方块自身的 `use`**） | 见下方「搭建链路」：目标机器是 `IMultiController` 时执行一次搭建；否则什么都不做 | 什么都不做（不读 NBT、不写世界） | **总是**返回「已消耗交互」的结果（无论有没有找到控制器），实际语义是 `InteractionResult.sidedSuccess(level.isClientSide)` |
| 潜行 + 右键 GT 控制器（未成型、**空手**） | GTM 自带功能 | 由 `IMultiController` 的默认 `onUse` 显示原地结构预览 | 渲染预览 | 与终端无关 —— 手里拿着终端时该分支不触发，所以终端不与它冲突 |
| 左键 / 攻击 / 与生物交互 / `onItemUseFirst` | — | 无任何行为 | — | 不消耗 |

要点：

- 搭建**只在服务端**执行，客户端只负责把交互「吃掉」，避免两端各搭一次。
- 潜行右键**任意**方块都会返回「已消耗」，也就是说：拿终端潜行右键一个不是控制器的方块，表现为「什么都没发生」，而不是打开终端界面。
- 终端**没有**「右键无线接入点绑定 AE 网络」的入口（现状如此，见 §6）。若新实现要走「终端自带 AE 链接」这条路，需要自己补一个入口（例如潜行右键无线接入点即绑定并提示）。

## 3. 设置项清单

### 3.1 八项设置

⚠️ **第一件必须记住的事**：这 8 个键直接写在**物品 NBT 的顶层**，**不在** `gtet_terminal` 子树里 ——
`gtet_terminal` 是另一棵单独的子树（放分级组 / 偏好 / AE 链接，见 §4）。两棵子树互不相干，别混。

| # | 显示名（中 / 英） | NBT 键 | 控件 | 取值 | 默认 | 语义 | 改了之后对搭建的具体影响 |
|---|---|---|---|---|---|---|---|
| 1 | 线圈等级 / Coil level | `CoilTier` | 步进器 | 0 ~ 线圈总档数 | 0 | 优先用第几档线圈（UI 值 1 = 最低档，依次递增；0 = 不指定） | 线圈格的候选按它换档，见下方「线圈格的候选规则」 |
| 2 | 重复结构次数 / Number of repetitions of the structure | `RepeatCount` | 数字输入框 | 0 ~ 1000 | 0 | 可重复结构（蒸馏塔、装配线等）的重复段放几次 | 只对「最小重复数 ≠ 最大重复数」的层生效：该层的实际重复数 = 把本值夹到 [最小, 最大] 之间；最小 == 最大的层恒等于该固定值，设置无效 |
| 3 | 无仓室模式 / No Hatch mode | `NoHatchMode` | 复选框 | 0 / 1 | **1** | 1 = 不主动放仓室（只在结构明确要求处放）；0 = 该放就放 | 见下方「仓室格判定」 |
| 4 | 线圈替换模式 / Coil replace mode | `ReplaceCoilMode` | 复选框 | 0 / 1 | 0 | 对**已成型**的机器，把已有线圈换成第 1 项指定的档 | 打开后：已成型机器也能触发搭建；碰到「该格已有线圈方块」时，先把旧线圈收进玩家背包再放新线圈；整轮结束后额外调用机器的 `onPartUnload()`。若旧线圈收不进背包（没有空位也没有可堆叠的位置）则跳过该格 |
| 5 | 使用 AE 物品 / Is use AE items | `IsUseAE` | 复选框 | 0 / 1 | 0 | 允许从 AE 网络取方块 | 见 §6 |
| 6 | 镜像搭建 / Mirror build | `IsFlip` | 复选框 | 0 / 1 | 0 | 结构按镜像摆放（左右或前后翻转） | 坐标映射里的 flip 位 = 本项 **或** 机器自身的 `isFlipped()`（原来只用机器自身那一位）。只影响摆放位置，不影响结构检测 |
| 7 | 模块搭建 / Module build | `Module` | 数字输入框 | 0 ~ 100 | 0 | 0 = 主结构；N > 0 = 第 N 套结构 | 决定这次搭**哪个图案**：0 → 用控制器当前的 `getPattern()`；N > 0 → 取第 N 套结构；取不到就静默退回主结构（不报错）。控制器只有一套结构时，任何非 0 值都等同主结构 |
| 8 | 拆除模式 / Demolition mode | `Demolition` | 复选框 | 0 / 1 | 0 | 反向操作：不放置，按结构拆掉该位置的方块 | 见 §5.4 |

关于「模块搭建」的语义补充：原实现**没有**单独的「主结构搭建」键、也没有单独一行 —— `Module == 0` 就是主结构。
新实现若要给它单独一行按钮，只需在 UI 上加一行写 0，语义不用动。

**读取约定**（原实现的实际写法）：所有键都以 `CoilTier` 是否存在作为哨兵 ——
「有 `CoilTier` 就逐个按存在读取，某个具体键缺失时退回该键的默认值；没有 `CoilTier` 就全部取默认值」。
新实现建议改成更稳的「每个键独立判存在」，但要保证与界面写入方式自洽（界面是逐键写入的）。
⚠️ 复选框在 NBT 里存的是 **int**（0/1），不是布尔。

**写入约定**：所有 NBT 写入只在服务端发生（客户端写自己背包物品的 NBT 不会同步回服务端）。
按钮与复选框的回调在两侧都会跑，所以原实现在回调里显式判「客户端就返回」；
数字输入框走 LDLib 的 client action 通道，最终由**服务端**那份控件执行回调，所以原实现没有额外判侧。

⚠️ **打开界面有一个副作用**：数字输入框控件在**构造时**会把自己的当前值夹一次并回写。
也就是「打开一次终端」就会把 `RepeatCount` 夹进 0 ~ 1000、把 `Module` 夹进 0 ~ 100。新实现要保持这一行为或明确改成不写，但必须知道有这一出。

**线圈格的候选规则**（实现「线圈等级」时的输入输出约定）：

- 输入：该格谓词给出的候选方块数组，以及 `CoilTier`。
- 判定「这是线圈格」的条件：候选里**任意一项**是 GTCEu 的 `CoilBlock`。
- 输出（线圈格）：`CoilTier == 0` → 候选 = 数组里除**最后一档**以外的全部（即不指定档位，且排除最高档）；
  `CoilTier == N > 0` → 候选 = 数组里的第 N 项（下标 N-1，越界则夹到最后一档）。
- 输出（非线圈格）：候选 = 原数组去掉空气。
- ⚠️ 这个「0 档时砍掉最后一档」正是 §4.5 那个「面板里选了却不生效」的根因。新实现如果自己重写这段，
  建议改成「0 档时给出全部档位」——这样面板键与搭建键天然一致，不再需要回退匹配。

**仓室格判定**（实现「无仓室模式」时的输入输出约定）：

- 输入：该格的候选方块数组 + `NoHatchMode`。
- `NoHatchMode == 0` → 一律允许放（返回「可以放」）。
- `NoHatchMode == 1` → 看候选数组的**第 1 项**：如果它是机器方块、并且它对应的机器是**多方块部件**
  （GTCEu 的 `MultiblockPartMachine`，即各种仓/总线/维护仓等）→ 返回「不要放」，否则「可以放」。
- 用途：搭建时，凡是「限次谓词要求的最小数量」之外的仓室位置都会被跳过；这样自动搭建不会把满结构塞满仓室。
- ⚠️ 判定只看候选的**第 1 项**，且「是不是多方块部件」需要一张方块集合（见 §8 的缺口说明）。

## 4. 右侧两块分级方块列表

### 4.1 数据来源：终端 NBT 的 `gtet_terminal` 子树

```
gtet_terminal                     （物品 NBT 下的一个 CompoundTag）
  plan                            上次 Shift+右键扫描到的控制器与分级组
    dim / x / y / z               控制器的维度与坐标（GlobalPos）
    groups                        组列表（ListTag of CompoundTag）
      key                         组键（字符串）
      candidates                  该组候选的物品注册名列表（ListTag of String）
  group_prefs                     玩家在面板里选好的档（ListTag of CompoundTag）
      group                       组键
      item                        物品注册名
  ui_group                        右下那块当前显示哪一组（字符串，组键）
  ae_link                         终端自带的 AE 链接（dim / x / y / z）；⚠️ 目前没有任何游戏内入口写它
```

- **组键算法**：把该组全部候选的物品注册名去重、升序排序，用 `|` 连接成一个字符串。
  面板、扫描、搭建三处**必须用同一个算法**（本仓已有 `StructureBuildPlanner.groupKey`）。
- **只显示候选数 > 1 的组**（单档组不算「分级方块」，三个读写位置都用这一条过滤）。
- **两组数据共存**：一份是预置的 6 类静态组（线圈 / 能源仓 / 超频仓 / 线程仓 / 并行仓 / 维护仓），
  一份是上次 Shift+右键扫描出的真实分级组。
  - 被动播种（每 tick）：已有组 + 静态组，**只增不减**，且**不动**任何 `group_prefs`；
    内容没变化时一个字节都不写（避免每 tick 触发物品同步）。
  - 扫描写入：`这次的扫描结果 ∪ 静态组` —— 扫描结果替换掉上一次扫描留下的陈旧组，但静态组永远不会被清掉。

### 4.2 两级联动规则

- 两块面板是**联动**的：右上选中的那一组，就是右下正在显示的那一组。
- 点右上某一行（图标/名字那一带）→ 写 `ui_group` = 该组键。**只在服务端写。**
- 点右上某行的 `[▶]` → 先写 `ui_group`（意图就是「我要调这一组」），再把该组的当前档循环到下一档（写 `group_prefs`）。
- 右下每个候选一行，勾上即把该档写进 `group_prefs`。
- 选中态存在**物品 NBT**里（服务端权威、随物品同步到客户端），不是界面本地字段：
  界面是服务端与客户端**各建一次**的，本地字段只有点的那一端会变（服务端那份会永远停在第一组），
  而且跨不了界面开关、也没法让两个终端各选各组。
- `ui_group` 在当前组列表里**找不到**时（旧存档、上次扫描的组被后来那次扫描覆盖、或者根本没点过）→ 退回第 1 组，不报错。
- 一组都没有 → 右下不显示任何行（只显示 §2.4 的空提示）。
- `group_prefs` 里记的物品**不在该组候选里**时 → 视为第 1 档。

### 4.3 每行渲染内容

| 面板 | 图标 | 名字 | 行尾 |
|---|---|---|---|
| 右上 | 该组**当前选中档**的方块 | 「▶ 」+ 该档物品名（非当前组用两个空格占位） | `[▶]` 按钮 |
| 右下 | 该候选方块 | 该候选物品名 | 勾选框（勾选态 = 该组当前选中档 == 本行候选） |

名字与图标都由**服务端求值后同步**给客户端（客户端的物品 NBT 会慢一拍，直接读会闪旧值）。
名字截断规则见 §2.4。图标悬停显示该物品的完整名字。

### 4.4 滚动与可见行数

每块列表 198 × 114，行高 16 → **可见 7 行**，多出的行靠滚动条（滚动条细节见 §2.4）。
换组时把滚动位置拉回顶部（否则会停在上一个组的滚动位置上）。

### 4.5 已知陷阱

1. **组与候选的可见性必须"全建出来、只换可见性与位置"**：
   LDLib 的控件树两端各建一次、数据按控件路径同步，所以树结构在界面存活期间必须完全一致 ——
   不能「按当前选中的组去建树」，只能「每组建一个子容器、全都建出来」，再按 `ui_group` 决定谁可见、谁被挪走。
   ⚠️ 被藏起来的容器必须挪到很远的上方（原实现用 y = -10000）：滚动区的最大高度是按**所有**子控件算的
   （不看可见性），只 `setVisible(false)` 不挪位置，滚动条会按「所有组加起来」的高度给出一大段空白。
2. **滚动高度要自己补算一次**：滚动区最大高度的自动重算挂在「子控件尺寸/位置变化」上，
   而第一次布局发生在控件初始化**之前**（那时会被"还没初始化"挡住），之后又因为「没变化」直接返回 ——
   不补算一次，最大高度会一直停在 0，候选一多就滚不动（看得见、够不着）。
3. **组键对不上 → 在面板里选了却不生效**：面板/扫描侧的组键来自「静态表或谓词原始候选」，
   而搭建侧的组键如果来自**经过设置加工后的候选**（典型：线圈格默认档砍掉了最高一级），两者就不相等。
   解决有两层：① 最稳的是让两侧都用「谓词原始候选集」算键（新实现推荐这么做）；
   ② 若要保留加工，必须保留一层「按候选集包含关系回退匹配」的兜底（见 §8 的 `lookupPreference`）。
   回退匹配只认「同一类部件的更具体 / 更宽泛版本」（两个候选集必须有交集，且一个是另一个的子集），
   命中多个时取交集最大的；偏好所属的组键在 `plan.groups` 里根本找不到时**不做回退、宁可不生效**。
4. 索引记的是**组键**（字符串）不是下标，所以扫描结果变化后旧选择可能失配 —— 失配的表现是「退回第 1 档」，
   不是报错。
5. 列表里的名字有缓存（按物品注册名缓存截断后的显示名），语言切换后不会刷新。

## 5. 自动搭建行为

### 5.1 触发链路

入口：**潜行 + 右键方块**（服务端）。整条链路的输入是「玩家 + 手上的终端物品 + 被右键的方块位置」。

1. **读设置**：从终端物品 NBT 顶层读出 §3.1 那 8 项。
2. **选图案**（受「模块搭建」影响）：
   - `Module == 0` → 取控制器当前的 `getPattern()`。
   - `Module == N > 0` → 取第 N 套结构（本仓的多结构 API 见 §8；GTM 本身没有多套结构的概念）。
   - 取不到第 N 套（控制器不支持多结构、下标越界、或实现内部抛异常）→ **静默退回主结构**，不报错。
   - 图案对象本身取不到（控制器没有图案、或读不到图案内部字段）→ 整次调用什么都不做。
3. **按状态分支**（受「拆除模式 / 线圈替换模式」影响）：

   | 条件 | 动作 |
   |---|---|
   | `Demolition == 1` | 执行一次搭建（此时是拆除语义，不管机器成型与否）→ 结束后清理一次多方块状态里的计数缓存 → **不**请求结构重检 |
   | 未成型 | 执行一次搭建 |
   | 已成型 且 机器是 `WorkableMultiblockMachine` 且 `ReplaceCoilMode == 1` | 执行一次搭建 → 额外调用 `onPartUnload()` |
   | 其它（已成型、没开线圈替换） | **什么都不做**（整次调用空转） |

4. **执行一次搭建** = 规划 + 放置（或拆除）。见 5.2 / 5.3 / 5.4。
5. **结构成型**：终端**不**主动触发结构重检。GTM 的多方块系统会周期性地重检「未成型 / 有错误」的结构
   （调度间隔由本仓配置 `multiblock.asyncCheckInterval` 控制，默认 250 毫秒；放置或区块加载后的首次检测延迟
   由 `multiblock.placementCheckDelay` 控制，默认 20 tick）。也就是说放完方块后机器会在下一次周期检测时成型。
   ⚠️ 补充事实：GTM 的 `IMultiController#requestCheck()` 只在**已成型**时才会真正重检，所以它对「刚搭完还没成型」的机器没用。

### 5.2 规划阶段 vs 放置阶段的分工

这是整节最重要的一条：**规划阶段不碰世界，放置阶段不做决策**。

| 阶段 | 输入 | 输出 | 是否改世界 | 本仓已有实现 |
|---|---|---|---|---|
| **规划** | 图案对象 + 控制器的多方块状态 + 世界（只读，用来判断哪些格子已经是空的） | 一份「格子清单」：每个待放置格子的世界坐标、候选方块列表、组键；外加「组键 → 组」的索引 | **不改** | `StructureBuildPlanner.plan(...)` |
| **放置** | 格子清单 + 玩家 + 终端物品 | 每个格子：选中的方块、方块来源（背包/AE）、放置成功与否、朝向修正；以及「缺什么」的统计 | 改 | `StructureBuilder.build(...)` |

规划阶段的细节（都是「取什么值」层面）：

- 遍历顺序 = 图案的三层结构（层 / 行 / 列）；层可重复的结构按重复次数展开（见 5.3 的重复次数）。
- 每个格子的**世界坐标**由「图案的相对坐标」经「结构方向 + 控制器的正面朝向 + 上朝向 + flip 位」映射得到，
  再平移到控制器坐标。⚠️ 这套映射**必须**与 GTM 结构检测用的映射完全一致，否则搭建出来的位置和检测的位置对不上。
  本仓 `StructureBuildPlanner` 里已经有这份映射（与控制器当前 `isFlipped()` 一致），新实现直接复用它、不要另写一份。
- 每个格子的**候选方块**按与 GTCEu 自身摆放逻辑相同的顺序取（限次谓词的「层内最小数量」优先，其次是
  「全局最小数量」，都不满足时取所有未越上限的限次谓词候选加上普通谓词候选），并剔除空气。
  本仓 `StructureBuildPlanner` 已实现这一套。
- 「已经有方块的位置」不进清单（只补空格）。
  ⚠️ 但**线圈替换模式与拆除模式还需要「当前已占用格子」的坐标与谓词**（否则换不了线圈、也拆不掉方块），
  这两种设置下遍历范围要覆盖全部格子，不能只取规划器的空格清单。

放置阶段的细节：

- 每个格子先按**分级组偏好**决定放什么：按组键（必要时走包含关系回退）找到玩家选的档；
  候选里有这一档就把它提到候选最前面；候选里没有、且「整格候选全是线圈」时插到最前面；
  都没有就用第 1 个候选。（本仓 `TerminalSettings.resolve(...)` 就是这件事，直接调用。）
- 然后**找方块来源**：背包（含嵌套容器）→ AE（受「使用 AE 物品」控制）→ 创造模式。
  找不到就**跳过这一格、继续下一格**，不中断整轮。
- 放置用 GTCEu/原版的方块放置流程（`BlockItem#place`，命中点用「未命中」、朝向向上）；
  返回 FAIL 视为没放成功，成功才扣物品。
- 整轮结束后对所有**成功放置**的位置做**朝向修正**：有 `FACING` 或 `HORIZONTAL_FACING` 属性的方块，
  依次尝试各朝向，选第一个「前方是空的（或还没被这次搭建占用）」的朝向；机器方块还要额外满足机器的朝向合法性。
  本仓 `StructureBuilder` 已实现。

### 5.3 四项设置分别作用在哪一步

| 设置 | 作用阶段 | 具体作用 |
|---|---|---|
| **模块搭建** | 第 2 步（选图案） | 决定这次搭哪个图案；取不到就退回主结构 |
| **重复结构次数** | 规划阶段的「层重复次数」 | 只对**最小 ≠ 最大**的层生效：该层实际重复数 = 把本值夹到 [最小, 最大]；最小 == 最大的层固定用它自己的值 |
| **镜像搭建** | 规划阶段的坐标映射 | 映射里的 flip 位 = 本项 **或** 机器自身的 `isFlipped()`；只改位置，不改检测 |
| **拆除模式** | 第 3 步（分支）+ 放置阶段的每一格 | 把「放置」整体换成「按结构拆除」，见 5.4 |

另外三项（线圈等级 / 无仓室模式 / 线圈替换模式）分别作用在放置阶段的「候选加工」「仓室格过滤」「旧线圈回收」上；
「使用 AE 物品」作用在「找方块来源」上。

### 5.4 拆除模式（`Demolition == 1`）

逐格语义（输入：该格的世界坐标 + 该格谓词 + 世界现状）：

| 该格现状 | 动作 |
|---|---|
| 谓词为空 / 谓词是「空气」/ 谓词是「控制器」 | 跳过（不拆） |
| 该格当前是空气 | 跳过 |
| 该格当前的方块**不属于**该格谓词的候选（候选 = 该谓词的普通候选 ∪ 限次候选，按方块对象比对） | **跳过**（这就是防「误删玩家方块」的那道闸） |
| 该格当前的方块属于候选 | 拆掉 |

- 拆分方块、**不产生原版掉落**，然后显式给玩家物品：先塞进玩家背包，塞不下就掉在方块原地（不会凭空消失）。
- 拆除模式下**不放置任何方块**，那一格「只拆不建」。
- 整轮结束后清理一次多方块状态里的计数缓存；**不**请求结构重检（拆到一半的结构不该被判成型）。
- 拆除分支在「成型与否」上都执行（否则一个已成型机器根本拆不动）。

与 GTO 的行为差异（已确认）：GTO 在开了「使用 AE 物品」时会先把拆下来的方块塞进 AE 网络，塞不进才给玩家；
**我们不做这件事** —— 拆除掉落永远给玩家/掉在地上。

已知风险（只能在游戏里最终验收）：

1. 判定用的是「该位置的候选方块集合」，所以**符合本结构谓词的分级机壳/线圈确实会被拆掉** ——
   这是拆除模式的意图；但如果玩家把本结构的机壳挪到别处当装饰，又在恰好落在同一谓词的位置上，就会被拆走。
2. 结构方块被拆掉后**原地放了别的方块**时，拆除模式不会清理它（不匹配候选），会留下残留 —— 这是拿安全性换的。
3. 掉落物进的是**玩家背包**，不走 AE（见上）。

### 5.5 失败 / 降级分支汇总

| 情况 | 表现 |
|---|---|
| 目标方块上的机器不是控制器 | 什么都不做（但交互已被消耗） |
| 控制器取不到图案 / 图案内部字段读不到 | 什么都不做，静默 |
| 模块档位取不到 | 退回主结构，静默 |
| 机器已成型且没开线圈替换 | 整次调用空转 |
| 某格找不到方块来源（背包 + AE 都没有） | 跳过该格，继续处理后面的格子，不中断 |
| 某格放置失败 | 视为没放，继续后面的格子 |
| 玩家在创造模式 | 不消耗任何物品；候选取第一个方块物品 |
| 拆除模式遇到非结构方块 | 跳过，不动它 |

### 5.6 与已有规格文档的差异

- 已有文档说「模块搭建」走**反射**去探第 N 套结构（先探 `getSubPattern()`，再探本仓的 `patternOfTier(int)`）。
  反射只是因为补丁 jar 不能依赖本仓的类。**新实现不需要反射**：直接调用本仓的多结构 API 即可（见 §8）。
- 已有文档把「重复结构次数」的上限描述为「UI 上限 1000，实际仍由层的重复范围夹住」——与代码一致，✅。

## 6. AE 取料

### 6.1 建造取料（当前真实行为）

- **什么时候要**：只在「使用 AE 物品」= 1，且玩家背包里（**递归地**，包括背包中各物品自带的容器）存在
  **已绑定接入点的 AE2 无线终端**（物品 NBT 里有 `accessPoint` 复合标签）时才可能走 AE。
- **要什么**：按该格候选顺序，逐个尝试从该网络取 1 个。
- **要不到怎么办**：继续试下一个候选；都不行就跳过这一格（不中断整轮）。
- **取料时机**：在「找到候选」的那一刻就**真的取走**（MODULATE），不是放置成功后再扣。
  因此**放置失败不会退回** —— 这是原实现的实际行为，新实现可以照做，也可以改成「先模拟、放置成功再扣」
  （本仓 `AeGridLink` 就是这个更安全的语义）。
- **优先级**：按背包槽位顺序扫描；每个槽位内部依次判「嵌套容器 → AE → 这个槽位里就是所需方块」。
  也就是说 AE 与背包谁先用，取决于无线终端所在的槽位顺序，**不存在全局优先级**。
- **创造模式**：完全不走背包与 AE，直接取候选里的第一个方块物品。

⚠️ 与已有规格文档的差异：已有文档写「手上是已绑接入点的 AE2 无线终端」——**不准确**。
实际是扫描**整个背包**（含嵌套容器），只要背包里（任何位置）有一支已绑定的 AE2 无线终端就生效。

### 6.2 拆除掉落

**不走 AE**：拆下来的方块一律给玩家（背包满则掉原地）。见 §5.4。

### 6.3 终端自带的 AE 链接（另一套机制，已接线）

本仓自己有一套「终端绑到某个网络」的实现（`TerminalSettings.linkAe / unlinkAe / getAeLink / hasAeLink`
与 `AeGridLink`），与 6.1 那套**互相独立**：

- 绑定目标可以是一个**无线接入点**（按其自身覆盖范围判定），也可以是一个**直连的 ME 方块**
  （要求玩家在 16 格以内）；判定时还要求维度一致。
- **只取不存**：整个类里没有任何存入路径。
- 取料语义更安全：先「模拟提取」判断够不够，放置成功后才真正提取。

✅ **已按「推荐后者」落地**（原状：`linkAe` / `AeGridLink` / `StructureBuilder` 全项目没有调用点，
「把高级终端绑到某个无线接入点」没有游戏内入口）：

- 绑定入口 = `AdvancedTerminalBind#toggle`，手势是**潜行右键**无线接入点 / 直连 ME 方块
  （潜行右键非控制器方块本来什么都不做，不与搭建抢交互）；再点同一格 = 解绑。
  它不另写一份判定，而是「临时写进 NBT → 让 `AeGridLink#resolveGrid` 解析一次 → 不通过就还原」，
  失败时按 `INACTIVE` / `OUT_OF_RANGE` 区分提示（不是 AE 方块则静默）。
- 取料 = `AdvancedTerminalBuilder` 解析网格 + `TerminalItemSource` 走 `AeGridLink#canExtract/extract`。
- ⚠️ `StructureBuilder` 仍是**死代码**（全项目只有它自己引用自己），保留待删——
  它与本终端的取料路径无关。

### 6.4 AE 相关的行为差异小结

| 项 | GTO | 原实现（GTMT 补丁） | 新实现（已落地） |
|---|---|---|---|
| 建造取料 | 有 | 有（背包里的 AE2 无线终端） | 有，但**只走 6.3**（终端自己的绑定）——没有实现 6.1 那条「读背包里的 AE2 无线终端」，因为接上 `AeGridLink` 后不再需要它 |
| 拆除掉落进 AE | 有 | **无**（永远给玩家） | 无（同原实现，掉落一律给玩家） |
| 取料时机 | — | 先扣后放（失败不退） | 先模拟；放置成功才提交，AE 侧**每种类型整轮只 `MODULATE` 扣一次**；放失败一个都不扣 |

| `installStaticGroups(ItemStack)` → boolean | 把 6 类静态组并进 `plan.groups`（只增不减，不动偏好）；没改动时返回 false 且不写 NBT |
| `cachePlan(ItemStack, BlockPos controller, ResourceLocation dimension, Map<String, List<String>> groups)`（无返回值） | 记录一次扫描：控制器位置 + （本次扫描结果 ∪ 静态组） |
| `getPlanTarget(ItemStack)` → `GlobalPos`（可能为 null） / `hasPlan(ItemStack)` → boolean | 上次扫描的控制器位置 |
| `cachedGroups(ItemStack)` → `List<GroupView>` | 界面用：组键 / 候选 id / 当前选中档（只含候选数 > 1 的组） |
| `cycleChoice(ItemStack, GroupView)`（无返回值） | 在某个组里循环到下一档 |
| `readGroups(CompoundTag plan)` → `Map<String, List<String>>` / `plannedGroups(ItemStack)` → `Map<String, List<String>>` | 读 `plan.groups` |

嵌套类型：`GroupView(String key, List<String> candidates, String chosen)`。

#### `StructureBuildPlanner` —— 规划（不改世界）

| 签名 | 说明 |
|---|---|
| **`plan(BlockPattern pattern, MultiblockState state, Level level)` → `Plan`** | 摊出「每个空格子要放什么」 |
| `groupKey(List<ItemStack> candidates)` → `String` | 组键：候选物品注册名去重、升序，用竖线字符连接成一个字符串（竖线即 ASCII 0x7C，面板键 / 扫描键 / 搭建键三处必须同一算法） |
| `itemId(ItemStack)` → `String`（可能为 null） | 物品注册名 |
| `itemStackOf(String itemId)` → `ItemStack`（可能为 null） | 注册名 → 物品栈 |

嵌套类型：

- `Slot(BlockPos pos, List<ItemStack> candidates, String groupKey)`，方法 `isEmpty()` → boolean。
- `Group(String key, List<ItemStack> candidates)`，方法 `tiered()` → boolean（候选数 > 1）、`defaultChoice()` → `ItemStack`。
- `Plan(List<Slot> slots, Map<String, Group> groups)`，方法 `slots()`、`groups()`、`emptySlots()`、`tieredGroups()`。

⚠️ 缺口（三条都必须在搭建驱动里补，见 §8.2）：

1. **只给出「空格子」** —— 已经有方块的位置**不进清单**（与「只补空格」的放置语义一致）。
   但「线圈替换模式」与「拆除模式」都必须看到**当前已有方块的位置**，所以这两种设置不能只靠 `plan(...)` 的输出；
2. 只按**最小重复数**展开，不支持「重复结构次数」；
3. 不做任何设置加工（线圈档位 / 无仓室 / 线圈替换），坐标映射里的 flip 位只认机器自身的 `isFlipped()`（不认「镜像搭建」设置）。

#### `StructureBuilder` —— 放置（改世界）

| 签名 | 说明 |
|---|---|
| **`build(Player player, BlockPattern pattern, MultiblockState state, ItemStack terminal)` → `Result`** | 一次完整搭建：规划 → 逐格决议 → 找来源（背包 → AE）→ 放置 → 朝向修正 |
| `summarizeMissing(List<ItemStack> missing)` → `Map<ItemStack, Integer>` | 把缺失物品按种类合并，便于提示 |

嵌套类型：`Result(int placed, int missing, List<ItemStack> missingItems, boolean aeLinked)`。

行为要点：创造模式不消耗；背包优先、AE 兜底（AE 是**先模拟、放置成功后才真扣**）；找不到来源的格子计入 missing 并跳过。

⚠️ 缺口：不支持拆除；用 `AeGridLink`（终端自带链接）而不是「背包里的 AE2 无线终端」；不支持重复次数/模块/镜像/线圈加工/无仓室/线圈替换；而且它只处理**空格子**（见上一条），所以线圈替换与拆除都要另写驱动。

## 9. 不需要移植的部分

下面 3 个 mixin + 1 个适配器，都是为「把补丁打在第三方 mod 上」而存在的，新实现里**不需要它们**
（这几个文件已于 2026-09-27 随 GTMT 一并删除，下表路径仅作历史记录）。

| 文件（项目相对路径） | 它绕开的问题 | 新实现为什么不需要 |
|---|---|---|
| `src/main/java/rain/gtetcore/gtet/mixin/GTMT/AdvancedTerminalBehaviorMixin.java` | 目标类不是我们的（第三方 mod 的物品行为类）。我们要在它的 `useOn` **前后**各插一件事：进入时把主手终端放进静态槽位（因为第三方的候选加工函数签名里没有物品栈，而它在 `useOn` 的调用栈里同步执行）；返回后把本次规划出的分级组写进终端 NBT | 自建物品的 `useOn` 就是我们自己的方法，这两件事直接写在自己的方法里，无需注入第三方类 |
| `src/main/java/rain/gtetcore/gtet/mixin/GTMT/AutoBuildSettingMixin.java` | 目标 `apply(BlockInfo[])` 是第三方的内部类方法，只会对线圈做等级替换；我们只能在它**返回后**把玩家选的档提到候选最前面 | 自建实现自己写候选挑选，直接在这一步读偏好即可 |
| `src/main/java/rain/gtetcore/gtet/mixin/GTMT/AdvancedBlockPatternMixin.java` | **版本错配桥**：第三方那个类是按**旧版 GTM** 编译的，字节码里把 `MultiblockState.getGlobalCount()/getLayerCount()` 的返回类型写死成 `Object2IntOpenHashMap`；而运行期 GTM 7.5.3 返回 `Reference2IntOpenHashMap`。两者在 fastutil 里**没有继承关系**（两条独立类型链），JVM 按「方法名 + 描述符」精确解析 → 每次自动搭建都会 `NoSuchMethodError`。桥的做法是在那两个调用点各加一个重定向，返回一个「活视图」 | **自建物品不存在这个问题**：我们的源码直接对着 GTM 7.5.3 编译，直接用 `Reference2IntOpenHashMap`（`StructureBuildPlanner` 就是这么写的）。这个 mixin 连同下面的适配器一起不要 |
| `src/main/java/rain/gtetcore/gtet/util/LiveGlobalCountView.java` | 上面那座桥的载体：一个继承了 `Object2IntOpenHashMap`、但把所有读写转发到 GTM 真表上的「活视图」（不能拷贝一份表，否则限次谓词的计数会在第二次读时失真） | 同上，随桥一起删除。⚠️ 它本身还有一条已知边界：迭代接口没有转发（若将来第三方开始遍历这张表，会静默看到一张空表）——删掉它就等于把这个隐患一并消掉 |

另外两件与「适配第三方」有关、新实现也**不该照抄**的事：

- 原实现为了让第三方编译期的字段可读，用反射去拼一个「继承 `BlockPattern` 的子类」；
  新实现**不需要**继承 `BlockPattern`（`StructureBuildPlanner` 用反射读图案内部字段就够，且它已经写好）。
- 原实现为了「候选加工函数拿不到终端物品」而引入静态上下文（`TerminalContext`），新实现不需要。

## 10. 未确认项

以下行为**靠读代码判断不出来**，或只有编译期/逻辑层证据、没有运行期证据，如实列出，不要当成已确认的事实。

> **2026-09-27 现状**：自建终端已经实现并可编译（见 §8.2），但**一次游戏都没启动过**——
> 终端界面的坐标、联动、绑定手势、配方可合成性全部未实机验证。下面的条目一条都没有被消掉，
> 第 1 条的这一结论对全部条目都成立。

1. **面板与搭建的联动交互没有任何运行时验证**：点上一行下面是否真的换组、`[▶]` 是否同时换组与切档、
   滚动条是否回到顶部、6 类静态组是否真的出现、选了某一档之后搭建是否真的用那一档 —— 这些原实现也只在
   编译期与逻辑层核过，**没有跑过游戏**。新实现已落地，同样只到编译期，必须实机验一次。
2. **`ui_group` 经物品 NBT 同步到客户端的那一拍延迟**：服务端写完到客户端看到新值之间隔多久，未实测。
3. **LDLib 版本差异**：本仓实际用的是 LDLib 1.0.50，而上面关于「文本框客户端输入怎么落到服务端」
   （client action 通道）的结论是在 1.0.29 的源码上读出来的。新实现确实自己包了文本框
   （`AdvancedTerminalUI` 里直接用 LDLib `TextFieldWidget`），需要在游戏里验一次
   「客户端输入是否真的写进了服务端 NBT」。
4. **滚动区最大高度的重算时机**：我们按「自动重算被挡在控件初始化之前」这一结论写成「首次布局后自己补算一次」，
   依据是对 1.0.50 的字节码核对，同样**没有运行时验证**。
5. **「是不是多方块部件」的判定方式没有实测过等价性**：原实现是遍历所有机器定义、逐个实例化机器再判
   「是不是 `MultiblockPartMachine`」（一次性开销未知，本仓没测过首次触发耗时）；用
   `PartAbility#getAllBlocks()` 之类的并集更便宜，但**是否与前者完全等价（会不会漏掉未登记能力值的部件）没有验证**。
   新实现选了**后者**：反射遍历 `PartAbility` 自己的静态字段，收集上面登记过的方块
   （`AdvancedTerminalBuilder`）——这个近似本身仍待实测，且**覆盖不到别的 mod 自己 new 出来的
   `PartAbility` 实例**。
6. **「重复结构次数」的合理上限**：1000 是原补丁把第三方原来的 99 提上去的，实际生效值仍被每层的重复范围夹住；
   用户到底需不需要 1000 未确认。
7. **搭完之后要不要主动触发结构重检**：现状是**不**触发，靠 GTM 的周期检测。
   另外 GTM 的 `requestCheck()` 只在**已成型**时才真正干活，所以它也无法用来"催"一个刚搭完的机器。
   是否要改成「搭建后主动轮询重检」未确认。
8. **物品图标控件的必要性**：LDLib 没有「只显示、不可交互」的物品图标控件，所以原实现自己写了一个带两端同步的。
   新实现自己写了一个（`client/terminal/ItemIconWidget`），它的行为同样未实测。
9. **列表里名字的缓存**：原实现按物品注册名缓存了截断后的显示名，语言切换后不会刷新。
   这是可观测行为，但「算不算 bug、要不要去缓存」未确认。
10. **快捷栏/副手场景**：原实现取的一直是**主手**物品，且播种器也只看主手。
    副手拿着终端时的行为（能不能开界面、能不能搭）没有确认过 —— 新实现明确**只支持主手**
    （播种器与界面都只看主手），副手场景仍属未覆盖、也仍是未确认项。

> 另外一条与本文档无关、但会影响实机验证的已知项：`✔`(U+2714) 等符号是否存在于 MC 默认字体未确认，
> 用到这类字符的控件在实机里可能只显示成一个方块。
