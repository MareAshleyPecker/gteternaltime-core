## 2. 仓的家族与整条链路

### 2.1 无线仓（给吃 EU 的机器供电）

按 **电压档 × 安培** 出品，每级电压都出下面这一整套：

| 类 | 安培 | 说明 |
|---|---|---|
| **小仓** | 1A / 16A / 64A | 普通能源仓范畴 |
| **大仓** | 256A / 1024A / 4096A / 16384A / 65536A / 262144A / 1048576A / **4194304A** | **激光仓范畴**，每档 ×4（`4194304 = 2²²`，是 256 × 4⁷ 的第 8 档）；**自己实现部件 + 自己的链路，不进 GTM 的激光管道体系**（所以也不受 GTM 自带激光仓只到 4096A 的限制） |

安培档数 = 3 + 8 = **11**；规模取舍**从 IV 起**，即 **IV / LuV / ZPM / UV / UHV / UEV / UIV / UXV / OpV / MAX（10 档）**
⇒ 合计 **110 个方块定义**。

### 2.2 时序族（给吃 TF 的机器供电）

| 件 | 干什么 | 容量 |
|---|---|---|
| **时序仓**（ETV 专属） | 把 TF 供给多方块 | **1h / 16h / 64h / 256h / 1024h / 4096h / 16384h**（7 档） |
| **动力仓** | **TF 版的输出仓**：把机器产出的 TF 往总控塔送 | — |
| 时序之瓶（物品） | 搬运 + 手持加速 | L1 / L2 / L3 = 1A ZPM / 1A UEV / 1A OpV |

时序仓容量（基准：**`1 TF/s` = 0.05 TF/t** ⇒ `1 秒 = 1 TF` ⇒ **1 小时 = 3,600 TF**；`1 TF = 8.192E+3 EU`）：

| 档 | 折算 TF | 折算 EU |
|---|---|---|
| 1h | 3.6E+3 | 2.9491E+7 |
| 16h | 5.76E+4 | 4.7186E+8 |
| 64h | 2.304E+5 | 1.8874E+9 |
| 256h | 9.216E+5 | 7.5497E+9 |
| 1024h | 3.6864E+6 | 3.0199E+10 |
| 4096h | 1.47456E+7 | 1.208E+11 |
| 16384h | 5.89824E+7 | 4.8318E+11 |

⚠️ 这条梯子**不和大仓的安培档一一对应**（早先那版理解错了）：它自己延续 —— **1h 之后直接跳到 16h**（×16），
之后每档 ×4，到 **16384h 封顶**（明确**不设** 4h 与 65536h）。

**谁产出 TF 由你定，我们只提供接口**：加一处「**配方类型是否产出 TF**」的登记（例：`ETTimeFlowRecipeTypes.producing(recipeType)` 或等价配置），
被标记的配方类型产出的 TF 由**动力仓**收走并送往总控塔。

### 2.3 整条链路

```
机器产出 TF ─[动力仓]→ 总控塔（存）
总控塔 ─[时序仓 1h~256h]────→ 吃 TF 的机器（超频仓 / 时间类机器）
总控塔 ─[无线仓 1A~4194304A]→ 吃 EU 的机器
                             同维度：主控塔直接分发
                             跨维度：主控塔 → 连接塔A ══连接塔B → 末端仓
时序之瓶 ─（绑定主控塔）─→ 搬运 / 手持加速（一次性的应急手段）
```

**投放规则（已定）**：TF **只给**"支持 TF 的机器"或"含支持 TF 的多方块" —— 不允许往任意机器里灌 TF。

### 2.4 仓怎么找到塔（已定：自动连 + 瓶子当绑定器）

| 场景 | 行为 |
|---|---|
| `masterTowerUnique = true`（默认） | **零操作**：全服只有一座塔，任何无线仓 / 时序仓自动连它 |
| `masterTowerUnique = false`（多塔） | **手持「已绑定的时序之瓶」右键仓**，把仓绑到瓶子指的那座塔；没绑的仓显示「**未接线**」、不取电 |

- **不新增绑定物品**：时序之瓶本来就"绑定到具体某座塔"，它天然就是那把钥匙 —— 右键塔绑定瓶子，
  再右键仓绑定仓，两步同一个人做。
- **绑定按玩家归属**：仓记下**放置者**的所有者身份，取电时校验塔的所有者 / 白名单；
  装了 **FTB Teams** 时**同队视为同一人**（队友的塔队友能用），没装就是纯单人判定。
  ⇒ 这是**软依赖**：`mods.toml` 里声明 `mandatory = false`，FTB Teams 的调用全部关在一个类里
  并按 `ModList.isLoaded("ftbteams")` 分派，缺它的时候 mod 照常加载。
- ⚠️ **自动连接那条路也要校验权限**，否则「没权限的玩家在唯一塔旁边摆一台仓」就能白拿 TF。
  手动绑定那条路在瓶子绑塔时已经验过一次，自动连接绕过了那一步，所以判定必须写在**取用的那一刻**。
- **两族读同一个「该连哪座塔」函数**（`MasterTowerRegistry#autoTower`）：无线仓与时序仓
  在自动连接上的行为**必须一致**，不然会出现「一种仓零操作能用、另一种仓必须先手动绑」的怪现象。

## 3. 换算

### 3.1 基础
- **单位定义：`1 TF = 1A IV × 1 tick = 8.192E+3 EU`**（IV = 8192 EU/t）。整条安培阶梯都是整数：

  ```
  1A IV=1        1A LuV=4        1A ZPM=16      1A UV=64       1A UHV=256
  1A UEV=1024    1A UIV=4096     1A UXV=16384   1A OpV=65536（瓶容量上限）   1A MAX=262144
  ```

- **四条换算关系**（都对得上，但别把"流量"与"存量"混着用）：

  | 关系 | 成立 | 说明 |
  |---|---|---|
  | `8192 EU/t = 1 TF/t` | ✓ **已定** | **阶梯整数**的来源（= 1A IV） |
  | `1 TF/s = 0.05 TF/t` | ✓ | 纯单位换算（1 秒 = 20 tick） |
  | `1 TF = 1 秒` | ✓ | **流量定义**：以 `1 TF/s` 流 1 秒 = 1 TF ⇒ `1 小时 = 3600 TF` |
  | `1 TF/s = 409.6 EU/t` | ⚠️ | 速率的能量当量落在这一条；**不是** `8192 EU/t`（差 20 倍），别混用 |

- ⚠️ 一条踩过的坑：把"1 TF = 1 秒"当成**存量**（1 TF 的能量 = IV 跑 1 秒 = `1.638E+5 EU`）时，
  阶梯会冒出 `0.2A / 0.8A / 3276.8 TF` 这种小数 —— 因为 `20 = 4 × 5`，因子 5 与 2 的幂阶梯除不尽，
  而且 1 TF 会等于 5A LuV。所以：**"秒"只用在流量与容量上，存量一律写 EU 或 秒/小时。**
- 换算**只在主控塔里**发生（塔是唯一闸口）；时流仓 / 链接仓只搬运，**不**顺手换汇。
  ⇒ 落地方式：塔对外提供「**给多少个 TF、换出多少 EU**」这一个入口（`ITimeFlowTower#extractTimeFlowAsEu`），
  仓只在 **TF 空间**算损耗（该扣多少 TF），**不在仓里调换算函数** —— 否则「唯一闸口」就破了。
- 充入效率 `η₁`、取出效率 `η₂`、往返 `η = η₁ × η₂`。

### 3.2 时序潮汐（框架先留，数值待你定）
- `rate(t) = 1 + a × sin(2π t / T)`，周期 `T` = 1 游戏日，均值 1。
- **汇率必须全局同相位**：否则跨维度就是第二条套利通道（便宜维度买、贵维度卖）。
- 实现上是**纯函数** `f(gameTime)`，所以**客户端能自己算**（时序之瓶的 tooltip 不必等同步包）。

### 3.3 反套利硬约束（要开潮汐，这两个数就不能各定各的）

```
不套利条件：  η × (1 + a) / (1 - a)  ≤  1
闭式解：      a  ≤  (1 - η) / (1 + η)
```

| 往返效率 η | 允许的波动半幅 a（上限） |
|---|---|
| 0.90 | 5.26% |
| 0.85 | 8.11% |
| **0.80** | **11.11%** |
| 0.75 | 14.29% |

建议基线：`η₁ = 100%`、`η₂ = 80%`；**在你定潮汐之前按 `a = 0`（关闭）实现**，配置项留着即可。

## 4. 超频仓吃时间流

**一句话设定**：超频 = 局部加速时间，所以烧的是时间流。这也解释了超频仓凭什么突破 ×4 能效定律 ——
它不是在用电，是在**借时间**。

- 现状：`OverclockHatchPartMachine` 声明 `overclockSpeed`（4/16/64/256/1024）与 `overclockEnergyFactor`
  （×0.25 ~ ×8），改写发生在 `MixinOverclockingLogic`。
- 新增：超频仓带**时间流缓冲**，真正吃到超频收益时按量扣：

  ```
  每次配方的时间流消耗 TF = (该配方因超频多出的 EU ÷ 8.192E+3) × k
  ```
  - `8.192E+3` = 1 TF（1A IV × 1 tick）：除以它就是把"多烧的电"折成"多少个 1A IV 的 tick"，再乘 `k`；
  - **`k = 0.5`（已定）**：付一半能量价值（五折），鼓励建塔；与瓶子那个 **4 倍**正好拉开 8 倍；
  - **取整下限 = 1 TF（已定）**：TF 用 long 存，`0.01 TF` 根本存不下 ⇒ 下限只能取整。
    （只影响极便宜的小配方；若确实要亚 TF 精度，内部改用"毫时流 mTF = 1/1000 TF"来存。）
- **不足时：退回标准超频**（你的决定），UI / Jade 提示；绝不允许"先超频后欠账"。
- 时间流来源：① 同一多方块里的**时流仓**（优先）；② 超频仓自己绑的主控塔。
- **扣费时机待核**：倾向**每 tick 按比例扣**（耗尽了当 tick 起降级），不会出现"超频已完成但燃料没了"。

## 5. 时序之瓶（显示 + 搬运 + 应急加速）

**一物三职**：

1. **显示转换率**：tooltip 显示当前 `rate`、潮汐相位、距峰谷时间、`1 TF = 8.192E+3 EU`、当前往返损耗 η、
   瓶内 TF 与其折算 EU。汇率是 `f(gameTime)` 的纯函数 ⇒ **客户端本地算**，不需要同步包。
2. **搬运**：把 TF 装进瓶里带走（跨维度只能靠这个，见下）。
3. **绑定主控塔 + 应急加速**（你这轮新增）：右键主控塔完成绑定；之后右键一台机器即可用 TF 换"时间"，
   让这台机器**立刻往前推进一段配方进度**——**非常亏**，定位是救急而不是常规玩法。

**"非常亏"怎么量化（已定口径 + 已定的系数）**：

```
手持加速消耗 TF = (这次推进本该消耗的 EU ÷ 8.192E+3) × K_hand        K_hand = 4（已定）
  其中"本该消耗的 EU" = 推进的 tick 数 × recipe.getInputEUt().getTotalEU()
  （推进是**跳过** tick 输入 ⇒ 这笔电玩家本来该花，现在用 TF 把它"买回来"）
⇒ 花掉的是 **4 倍**能量价值的 TF、换回 1 倍本该消耗的电（净亏 3 倍）；
   对照超频仓 `k = 0.5`（五折）—— 手持加速比走超频仓贵 **8 倍**。
```

⚠️ **口径必须按 EU 补扣，不能按"秒"计费**：按秒计的话，1 秒机器时间（IV 档值 `1.638E+5 EU`）只收
`K_hand` 个 TF，`K_hand = 4` 时等于 `×0.2` —— **比直接换电还便宜 5 倍**，瓶子会变成最优解；
要同样"亏 4 倍"就得把 `K_hand` 抬到 **80**（= 4 × 20）。与其抬系数，不如用 EU 口径：系数与等级无关，一套算式通吃。

**能加速到什么范围（要如实说清）**：真实边界是**所有走 GTM 配方逻辑的机器**（`RecipeLogic` / `IWorkable` 系）——
整合包里的产线机器基本都是这一类；纯 AE 方块、别的 mod 自己的机器若没有加速接口就加速不了
（除非我们逐个 mixin，那不值得）。所以"任意机器"= **"任意 GTM 机器"**。

**TF 从哪扣（已定）**：**同维度直接从绑定的塔扣**（绑定才有意义，也不用手动充装）；**跨维度只能用瓶内 TF**
（先在塔旁充装再拎过去，搬运有成本）。两种都要求**塔所在的区块已加载** —— 与"链路两端都要加载"保持一致，
不破例做强加载。

**瓶容量（已定：L1 / L2 / L3 = 1A ZPM / 1A UEV / 1A OpV）**：容量按「**整数安培 × 电压 × 1 tick**」给，
不用"小时"（按 1A 讲话，玩家不用换算就能跟能源仓对比）：

| 档 | 容量 | 折算 TF | 折算 EU |
|---|---|---|---|
| **L1** | 1A ZPM | 1.6E+1 | 1.3107E+5 |
| **L2** | 1A UEV | 1.024E+3 | 8.3886E+6 |
| **L3**（上限） | 1A OpV | 6.5536E+4 | 5.3687E+8 |

相邻档正好 **×64**（ZPM → UEV → OpV 各差 3 个电压档，4³ = 64），所以 L1 到 L3 跨两个数量级。

（换算基准：`1 TF = 1A IV × 1 tick = 8.192E+3 EU`，**按 1 tick 计算** —— 已定。）

**形态（已定）**：**一件物品、按升级提升** —— 基准是 L1，用升级件升到 L2 / L3；升级只抬容量上限，
物品本身不换、瓶内 TF 不丢。

待定的小点：三档做成**一件物品按升级提升容量**（我按这个写）还是**三件独立物品**（与本仓"每档一件方块"的
仓室族风格一致）。

**加速形态：A（已定）** —— 一次性推进当前配方进度。B / C 列在下面只为记录取舍，以后想加再说：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（已定）** | 一次性推进当前配方进度（右键一次、按瓶内/塔内 TF 换算） | 无持续状态、无性能负担、好预算、亏得自然 |
| B | 持续 N 秒的加速倍率（期间额外烧 TF） | 手感更爽，但要维护临时状态与卸载/存档 |
| C | 区域时停/加速（一片机器同时加速） | 最好玩也最难：性能、平衡、误伤都麻烦 |

## 6. 主控塔唯一性（配置项）与同维度距离税（中和方案）

### 6.1 唯一性
- `masterTowerUnique`，**默认 `true`**：`true` = 全服唯一（第二座不成型并提示）；`false` = 允许很多座。
- 关闭唯一性时，**每座塔各自独立记账**（各存各的 TF），链路与时序之瓶**绑定到具体某座塔**。
  ——不要做成"多塔共享一个池"，那需要网络合并，复杂度不成比例。
- ⚠️ 从 `false` 改成 `true` 时，**已存在的多座塔不追溯**（继续工作），只是新塔不能再成型。
- **所有者 + 白名单（已定）**：塔有所有者，白名单决定谁能换汇、谁能取用（多人服防"先到先得"）。
- **拆塔时把储备封存成物品（已定）**：避免单点故障把全服时间流一起炸没。

### 6.2 同维度距离税：中和方案
你说 ① 和 ② 中和一下——做法是**软拐点 + 上限**：短中距离让线缆占优，超远距离塔仍然占优，
而**交叉距离本身就是旋钮**。

```
损耗% = 基础损耗（按档位 2% ~ 8%）
      + clamp(距离 − 免计距离, 0, 上限距离) / 上限距离 × 距离系数上限
已定：免计距离 = **128 格（8 区块）**、上限距离 4096 格、距离系数上限 +15%
```

- **≤ 128 格（8 区块内）**：只有基础损耗，而线缆近距离几乎无损 ⇒ **线缆仍是首选**（这就是你要的"8 区块"）；
- **128 格以上**：距离项开始爬，到 4096 格封顶 +15% ⇒ 塔逐渐反超；
- **> 4096 格**：距离项封顶，塔的总损耗固定；而线缆损耗**无上限累积** ⇒ 超远距离塔稳赢。

具体交叉点要按**线缆损耗模型**标定（GTM 的线损算法我还没核，列为动手前的待核项）。

想让"电网感"更强，就把**免计距离调大 / 距离系数调小** —— 一个旋钮，不用改结构。

### 6.3 连接塔与跨维度损耗

- 基础跨维度损耗 **10%**；**连接塔 4 ~ 6 个配件槽**，每个配件把**当前**损耗**减半**，地板 **0.1%**。
- 为什么不用"每级 -3%（绝对值）"：10% − 3%×4 = −2%，4 个槽就见底、后两个槽白装；
  改成乘性后：4 槽 = 0.625%、5 槽 = 0.3125%、**6 槽 = 0.156%**，再往上到 7 槽 = 0.078% 才被 0.1% 的地板夹住。
- 配件**不压时滞**（时滞只跟塔 / 仓的档位走），保持简单。

### 8.1 三条"动手前必须先试" —— **已全部验完**

| # | 问题 | 结论 | 证据 |
|---|---|---|---|
| 1 | TF 做成一等 `RecipeCapability` 要 Mixin 吗？ | **不要**。走 `IGTAddon#registerRecipeCapabilities()`（`GTRecipeCapabilities.java:32` 的回调，落在 `:24 unfreeze` 与 `:35 freeze` 之间），本仓 `ETGTAddon` 已实现该接口 | `run-data/logs/latest.log:412` 回调、`:442` 自检：`[GTET] time flow recipe capability: registered` |
| 2 | TF 不足会自动 SUSPEND 吗？ | **不会**。`RecipeRunner` 失败时确实回填 `fail(null, capability, io)`（`:238`），但自动 SUSPEND 分支只认 `EURecipeCapability`（`RecipeLogic.java:294-295`）⇒ TF 不足只是 WAITING，**降级逻辑必须我们自己写** | 已核 |
| 3 | 能和 GTM 能源仓混装吗？ | **能**。压缩规则把「除 1A 外、4 的幂次」的安培折成 `1A × (电压×安培)`，我们的阶梯恰好全是 4 的幂 ⇒ 与 GTM 自家多安培仓表现一致；**代价是整机档位会被抬高** | `EnergyContainerList.calculateVoltageAmperage` + `WorkableElectricMultiblockMachine#getMaxVoltage` |

**顺带一条环境坑**（会白白浪费一整天）：同一仓库里**并发跑 Gradle 会清空 `build/classes`**，症状是
`this.modClass is null` 或 `NoClassDefFoundError`；把 `classes` 与 `runData` 放进**同一次** invocation 即可。
