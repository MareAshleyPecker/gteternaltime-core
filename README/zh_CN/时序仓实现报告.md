## 2. 七档的方块 id 与容量

### 变体表（`ETTimeFlowHatches.kt:120-126`，数值即设定 §2.2 定稿值）

| `gtetcore:tf_hatch_16h` | UHV | 16 | 57,600 | 4.7186E+8 |
| `gtetcore:tf_hatch_64h` | UEV | 64 | 230,400 | 1.8874E+9 |
| `gtetcore:tf_hatch_256h` | UIV | 256 | 921,600 | 7.5497E+9 |
| `gtetcore:tf_hatch_1024h` | UXV | 1024 | 3,686,400 | 3.0199E+10 |
| `gtetcore:tf_hatch_4096h` | OpV | 4096 | 14,745,600 | 1.2080E+11 |
| `gtetcore:tf_hatch_16384h` | MAX | 16384 | 58,982,400 | 4.8318E+11 |

```kotlin
// ETTimeFlowHatches.kt:120-126
TimeFlowHatchVariant("tf_hatch_1h", 1, 3_600L, GTValues.UV),
TimeFlowHatchVariant("tf_hatch_16h", 16, 57_600L, GTValues.UHV),
...
TimeFlowHatchVariant("tf_hatch_16384h", 16384, 58_982_400L, GTValues.MAX),
```

- 表里的第三列 `capacityTf` 与第二列 `hours` **由构造函数里的 `require` 强校验**
  （`ETTimeFlowHatches.kt:74-78`：`capacityTf == hours × ETTimeFlow.TF_PER_HOUR`）——
  这是照线程仓那张表「规格必须自己对上」的约定加的护栏，写错一行直接炸在类初始化上，
  不会变成「名字写 16h、仓里其实装 1h」。
- 容量公式 `容量 = 小时 × 3600`（`ETTimeFlow.TF_PER_HOUR`），**不引入新常量**。

### ⚠️ 电压等级是推断（需要你确认）

设定 §2.2 只写「时序仓（**ETV 专属**）」，没说每档挂哪个电压等级。而 GTM 7.5.3 的 `GTValues` 最高到
`MAX`（= 14），**没有 ETV 这一级**（`README/zh_CN/对照表.md` 里 ETV = MAX 的 4 倍 = 8589934592 EUt）。
7 档容量正好对上 `UV..MAX` 这 7 个实体等级，且与线程仓族的上界一致，所以先这么落
（`ETTimeFlowHatches.kt:107-112` 写了这段推断与「将来 ETV 成为真实等级时只改这一列」）。**若你要改成别的区间，改变体表第三/四列即可，id 与容量都不用动。**

### 部件怎么持有 TF

**持有**：本体只有一个 `ETTimeFlowHandler` 实例，没有第二份缓冲（`TimeFlowHatchPartMachine.kt:85`）：

```kotlin
val tfHandler: ETTimeFlowHandler = ETTimeFlowHandler(0L, capacity)
```

`ITimeFlowStorage` 就是它的门面（`:169-184`）：读 `tfHandler.amount`、容量读 `tfHandler.capacity`、
写走「先 `extract(Long.MAX_VALUE)` 清空、再 `insert(夹取后的值)`」（`ETTimeFlowHandler` 只给了
`insert`/`extract` 两个口子，故意没有写第二个 setter）。
`init` 里还挂了一个变更监听（`:126-128`）：**存量一变就 `markDirty()`**
（拉塔灌入 / 配方扣掉 / 手动取出都会走到），保证区块存档写的是最新值。

### 怎么把 TF 暴露给配方（接线那几行）

```kotlin
// TimeFlowHatchPartMachine.kt:93  —— 处理器列表只建一次并复用
private val recipeHandlers: List<RecipeHandlerList> = listOf(RecipeHandlerList.of(IO.IN, tfHandler))

// TimeFlowHatchPartMachine.kt:200 —— 交给所在多方块
override fun getRecipeHandlers(): List<RecipeHandlerList> = recipeHandlers
```

两条链路说明：

- **谁读它**：`WorkableMultiblockMachine#onStructureFormed` 遍历 `getParts()`，对每个部件
  `part.getRecipeHandlers()` → `addHandlerList(...)`（javap 实证过：`:155` 调 `IMultiPart.getRecipeHandlers()`，
  `:209/:394` 调 `addHandlerList`）。**多方块那一侧一行都不用改**。
- **为什么要覆写 `getRecipeHandlers()`**：`MultiblockPartMachine#getHandlerList()` 只把
  **同时是 `MachineTrait`** 的 trait 收进列表（javap 实证：它对 `traits` 逐个 `instanceof IRecipeHandlerTrait`），
  而 `ETTimeFlowHandler` 刻意**不**继承 `MachineTrait`（它自己的类注释写了理由）。
  但 `IRecipeHandlerTrait` 本身就是 `RecipeHandlerList` 能收下的形态，所以直接自建一个列表返回。
- 扣费本体仍然是 `ETTimeFlowHandler#handleRecipeInner`（**没有第二份 TF 扣费实现**）：
  配方 `tickInputs` 带 TF 时，每 tick 以 `simulate=false` 被调一次。

## 3. 从塔拉 TF 的 tick 路径

| 项 | 内容 |
|---|---|
| 入口方法 | `TimeFlowHatchPartMachine.pullTick()`（`:220`） |
| 频率 | **每服务端 tick 一次**；由 `ConditionalSubscriptionHandler`（`:123`）订阅，**条件 = 已绑定塔**（`:124`），未绑定自动退订 |
| 订阅怎么建 | `onLoad()` 里 `tickSubscription.initialize(level)`（`:335-338`）——⚠️ 这一步必须显式做：`ConditionalSubscriptionHandler` 只在 `initialize` 里把订阅排到服务端线程上（GTM 自己的 `ConveyorCover#onAttached` 也是这么调的）；绑定/解绑时再 `updateSubscription()` 一次（`:145/:163`） |
| 找塔 | `TimeFlowTowers.find(lvl, bound.pos())`（复用既有设施：它内部先 `level.isLoaded(pos)` 再 `MetaMachine.getMachine`） |
| 取 TF | `tower.extractTimeFlow(本仓剩余空间)`（`ITimeFlowStorage` 的契约：不够就有多少给多少），拿到多少就 `tfHandler.insert(...)` |
| **拉不到时** | **静默返回**，不刷日志、不报错、不弹提示（区块滚出视野是常态）。只有四条「不拉」：客户端 / 缓冲已满 / 未绑定 / **维度不同** / 找不到塔 |

```kotlin
// TimeFlowHatchPartMachine.kt:220-238（节选）
if (isRemote) return
val lvl = level ?: return
val room = getTimeFlowRoom(); if (room <= 0L) return
val bound = getBoundTower() ?: return
if (bound.dimension() != lvl.dimension()) return           // 跨维度不拉（设定 §5）
val tower = TimeFlowTowers.find(lvl, bound.pos()) ?: return // 未加载 / 不是塔 → 静默
val got = tower.extractTimeFlow(room)
if (got > 0L) tfHandler.insert(got)
```

**只搬运、不换汇**（设定 §3.1）：仓里不做充入 / 取出效率，折损只发生在主控塔那个唯一闸口。

### 绑定怎么绑（复用塔那套绑定数据结构）

- 绑定状态 = 四个 `@Persisted` 字段（`:100-118`）：`boundDim`（`ResourceLocation` 串）+ `boundX/Y/Z`，
  与 `TimeBottleData` 的 NBT 键同构，`getBoundTower()`（`:132`）拼回 `GlobalPos`。
- 手势（`IInteractedMachine#onUse`，`:252-294`）：**手持已绑定主控塔的时序之瓶右键本仓 = 绑定；潜行右键 = 解绑**。
  瓶子的绑定照旧是「手持瓶子右键塔」（上一轮已做）。这样两步就完成，**不新增任何物品或 GUI**。
  - 为什么用 `onUse`：javap 实证 `MetaMachineBlock#use` 里它是
    `instanceof IInteractedMachine → onUse`（`:290-331`），**排在 `tryToOpenUI`（`:370`）之前**，
    返回非 `PASS` 直接 `areturn` —— 不会被部件 UI 吃掉。
  - 瓶子没绑塔 / 塔在别的维度：只发一条 action bar 提示，右键**交还给方块**（返回 `PASS`）。
- 存档：绑定走 `@Persisted`；**TF 存量走 `saveCustomPersistedData` / `loadCustomPersistedData`**（`:305/:316`）。
  理由写在类注释里、也在这里再说一遍：TF 的真值在 `ETTimeFlowHandler#amount` 里，而它**不是 LDLib 的 `IManaged`**，
  标不了 `@Persisted`；而 `IAutoPersistBlockEntity#saveManagedPersistentData` 的顺序是
  **先写 `@Persisted` 字段、最后才回调 `saveCustomPersistedData`**（javap 实证：`:101 invokeinterface saveCustomPersistedData`；
  `loadManagedPersistentData` 同理：`writePersistedFields` → `loadCustomPersistedData`）
  ⇒ 把 handler 的值镜像进 `@Persisted` 字段会**慢一截**（配方扣费发生在**别的机器**的 tick 里），
  直接走自定义数据通道才是零误差的。主控塔的储备也是走的同一条通道。
- `getFieldHolder()` 照 `ThreadHatchPartMachine:157-161` 的写法挂在 `MultiblockPartMachine.MANAGED_FIELD_HOLDER` 后面（`:347/:362`）。

## 4. 谓词 mixin 加了什么、为什么这样加

**加了什么**（`MixinPredicatesAutoAbilities.java:84-88`）：

```java
// 时序仓同规格：一台多方块一个 TF 仓就够（两个仓会自动合池，见 ETTimeFlowHandler#handleRecipeInner）
TraceabilityPredicate timeFlowHatch = Predicates.abilities(ETPartAbility.TF_HATCH)
        .setMaxGlobalLimited(1)
        .setPreviewCount(1);

cir.setReturnValue(original.or(overclockHatch).or(timeFlowHatch));
```

**为什么这样加**（照原注释那份思路写的四条，全部落在文件注释里）：

1. **为什么走这里而不是让机器自己加槽**：多方块能插什么只由结构谓词决定；部件自己的
   `MachineBuilder#abilities(...)` 只声明「我属于哪个能力」，不会让任何结构接受它。
   走这里 = 对**所有**调 `autoAbilities(_,_,true)` 的多方块生效（GTM / GCYM 的机器都在内）；
   走机器自己的谓词 = 只对那台机器生效。
2. **时序仓是「全局可插」的设计**（设定 §8.3 把这条列为必做接线），而且它插上去**一定生效**：
   只要配方里有 `time_flow` 的 tick 输入，扣费就走仓自己的 handler，与多方块是不是 GTET 的无关。
   这与线程仓相反 —— 线程仓只在实现了 `IThreadedRecipeMachine` 的机器上有意义，
   所以它继续由 GTET 自己的多方块显式加槽（`ETTestMultiblocks` 的 `'X'`）。
3. **只改 `autoAbilities(ZZZ)` 这个重载**：其它重载压根不加 `PARALLEL_HATCH`，那些多方块本来也插不了并行仓。
4. **⚠️ 顺序约束**（原注释没有，这次补的）：`PartAbility#getAllBlocks()` 是**懒记忆化**的快照，
   而 `Predicates.abilities(...)` 在**构造谓词那一刻**就把它取出来
   （javap 实证：`Arrays.stream(...).flatMap(...).toArray(...)` 立即求值）。
   今天这不会提前发生（多方块图案是 `Supplier`，运行期才构造），但前提是
   **`ALLSmachine.init()` 仍早于一切用到本能力的图案构造** —— 已确认 `MachineRegister` 里
   `ALLSmachine.init()` 在 `ALLMmachine.init()` 之前，且本次新增的仓也注册在 `ALLSmachine` 里。

**这条改动在 datagen 里被实证到了**（不是只靠读码）：`GTETDataReport` 的能力自检调了一次
`Predicates.autoAbilities(true, false, true)`，日志出现

```
[mixin/]: Mixing GTM.MixinPredicatesAutoAbilities from gtetcore.mixins.json into com.gregtechceu.gtceu.api.pattern.Predicates
```

且产物里（见第 5 节）`tf_hatch_found_in_predicate = 7`
—— 也就是**该谓词的全部候选方块（42 个）里，7 个时序仓都在**。这证明：能力登记成功 + mixin 注入成功 + 谓词把仓摆进了结构槽。

顺带一条：`PartAbility.TF_HATCH` 的 `getAllBlocks()` 在自检那一刻是 **7 个**，与注册数一致。

### 这条 JSON 是怎么出来的（⚠️ 与任务描述的差一处，必须说清）

任务写的是「用 runData 生成配方 JSON」。**GTM 的配方本来就不走 datagen** ——
`IGTAddon#addRecipes` 只在 `AddPackFindersEvent` 里被调（`GTRecipes.recipeAddition` → 内存里的
`GTDynamicDataPack`），而 `runData` **不发**这个事件：本次日志里既没有 `GregTech Data loading took`，
也没有任何 GTET 配方被写盘（前几轮的产物里同样一条配方 JSON 都没有）。
仓库里 `GTETDatagen` 的注释早就记了这条路为什么会崩：`GTRecipeBuilder#toJson()` 第一件事就是
`GTRegistries.builtinRegistry()` → `GTCEu.isClientThread()` → `Minecraft.getInstance().isSameThread()`，datagen 下 NPE。

所以这次的做法是：**新增一个 datagen provider，用 GTM 自己的那个 codec 把配方序列化出来**
（`GTETDataReport`，`GTETDatagen` 注册）。要点：

- 用的是 `GTRecipeSerializer.CODEC` —— **和 `GTRecipeBuilder#toJson()` 内部用的同一个 codec**（javap 实证）；
- 唯一换掉的是 `RegistryOps` 的注册表来源：从 `GTRegistries.builtinRegistry()`（会 NPE）
  换成 datagen 给的 `GatherDataEvent#getLookupProvider`；
- **序列化本身一个字节都没有自己拼**：`"tickInputs": { "time_flow": [...] }` 这个键是
  GTM 的 codec + 我们注册的 `ETTimeFlowCapability`（其序列化器是 `Codec.LONG.xmap(...)`）一起产出的；
- 产物里**同时**留了对照项 `gtm_toJson_error`：那条空指针的原文，把「为什么不能走 GTM 的 toJson」
  从注释变成了可复核的产物。

⇒ 这条链验到的是：**能力注册 → 配方序列化 → 写盘**。
**没验到**的是：游戏里真的加载这条配方并扣掉 TF（那要开游戏，见第 6 节）。

  所以本文件补了一个**同形的小扩展** `GTRecipeBuilder.tickInput(cap, stack)`（`:83-92`），
  实现照抄 `EUt(long)`：存旧值 → 置真 → `input(...)` → 还原。

## 7. 没验成 / 存疑（诚实清单）

**一次游戏都没跑过。** 下面全部只有静态证据 + datagen 证据。

1. **配方在实机里是否真的每 tick 扣 TF —— 未确认。** 验到的是「序列化出来带 `time_flow` 的 tick 输入」，
   没验到的是「配方跑起来后仓里真的少 TF」。
   卡在哪：要开游戏（摆多方块、给仓灌 TF、看存量下降）。扣费链条本身（`RecipeLogic#handleTickRecipe`
   → `RecipeRunner` → `handleRecipeInner`，`simulate=false`）是上一轮 javap 核过的，本轮没有新增证据。
2. **仓的绑定与拉塔 —— 未确认。** 三条子项：
   ① `onUse` 手势在实机里的手感（会不会被别的交互抢走）未验；
   ② `ConditionalSubscriptionHandler.initialize(level)` 在部件 `onLoad()` 里调用是否足够（GTM 的
   `ConveyorCover` 是同样调法，但它不是部件机器）未验；
   ③ 塔侧 `extractTimeFlow` 被跨机器每 tick 调用时的表现（塔未成型 / 正在换汇同一 tick）未验。
3. **结构能不能真的插进去 —— 半验。** datagen 里已证明 `autoAbilities(true,false,true)` 的候补方块含 7 个时序仓
   （`tf_hatch_found_in_predicate = 7`），但「实机把仓放上去、结构检测通过、JEI 预览正确」未验。

   （先写 `@Persisted` 字段，再 `saveCustomPersistedData`），但「拆下来再装回去数值还原」没跑过。
   另外 `@Persisted` 只落盘、**不同步到客户端**，所以绑定状态在客户端看不到（本轮没有做面板）。
