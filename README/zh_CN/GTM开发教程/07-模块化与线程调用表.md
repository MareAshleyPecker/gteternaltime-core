# 案例七（调用表）：模块化与线程怎么接
> [← 返回目录](<../GTM开发教程(编写中).md>) ｜ [上一节：06 游戏内怎么用](06-游戏内怎么用.md)

这一节是**写给调用方的接线表**：想新写一台**模块化**多方块、或者想让它**支持线程**时，
「继承什么 → 覆写什么 → 每个成员的契约 → 在哪注册」逐条对着抄。
括号里的 `文件:行号` 都是本仓库源码里核对过的位置（GTM 的行号沿用 [05 速查](05-API调用速查.md) 已核对的那批）。

> ⚠️ 先说清楚「模块化」在本仓库里有**三套不同的东西**，别混：
>
> | 叫法 | 基类 | 语义 | 现状 |
> |---|---|---|---|
> | **模块物品 → 等级 → 第 N 套结构** | `ETModularMachine`（`ETModularMachine.kt:32`） | 往模块槽放一个物品，物品的等级同时决定**结构**与**配方电压上限** | **活样本：模块化测试机**（`ETModularTestMachine.kt:47`）；本节主角 |
> | **主机 + 单元（一套机器拆两台）** | `ETModuleHostMachine`（`ETModuleHostMachine.kt:18`）+ `ETModuleMachine`（`ETModuleMachine.kt:35`） | 单元 32 格内找主机，借主机的电、继承主机的等级 | 两个抽象基类都**还没有注册任何子类**（只被 [04](04-模块化机器代码案例.md) 当代码案例用） |
> | 控制器 + 接口仓 | GTM 原生 `Predicates.abilities(...)` | 部件就是功能模块 | 见 [02](02-模块化的多方块.md) |

## 1. 继承什么、必须实现什么

### 1.1 类与接口

| 要什么 | 写什么 | 位置 |
|---|---|---|
| 模块物品决定等级的模块化多方块 | `class X(holder: IMachineBlockEntity) : ETModularMachine(holder)` | 基类 `ETModularMachine.kt:32`，父类 = `WorkableElectricMultiblockMachine` |
| 支持多线程 | 上面那个类**再加** `, IThreadedRecipeMachine` | `IThreadedRecipeMachine.kt:27`（`extends IMultiController`） |
| 只写台普通多方块（不要模块化、不要线程） | 照 [05 §1](05-API调用速查.md) 注册即可，本节不涉及 | — |

### 1.2 `ETModularMachine` 的成员契约

| 成员 | 谁实现 | 参数 / 返回 | 什么时候被谁调 | 非法值会怎样 |
|---|---|---|---|---|
| `moduleSlot`（`:35-40`） | 基类给，**子类必须摆到 UI 上** | `NotifiableItemStackHandler`，容量 1、`IO.NONE` | 内容一变就 `onContentsChanged` → `onModuleChanged()`（`:36-39`） | 不摆到界面 = 玩家没地方放模块，机器永远 0 档 |

| `tierOfModule(stack)`（`:54`） | `protected open`，**默认走 `ETModuleTiers.tierOf`** | 入参模块物品栈；返回等级，`0` = 不是合法模块 | `onModuleChanged()` 里每变一次调一次（`:78`） | 返回 0 = 结构不成型（不是报错） |

| `maxRecipeTier()`（`:65`） | `open`，默认 `moduleTier - 1` | 返回允许的配方电压档位；**返回 `< 0` = 不限** | ① `ETModularRecipeLogic.matchRecipe`（`:122`）② 面板显示（`ETModularTestMachine.kt:84`） | 返回 -1 时不做等级拦截（`:123` 的 `cap >= 0 &&` 短路） |

| `checkPattern()`（`:71`） | `open`，默认 `moduleTier > 0 && super.checkPattern()` | `Boolean` | 结构检测 | 覆写时务必保留「0 档不成型」这一条 |

| `onModuleChanged()`（`:76-85`） | 基类给，`public` | 重算等级 → `requestCheck()` → `markLastRecipeDirty()` → `updateTickSubscription()` | 模块槽内容变化；也可以自己手动调 | — |

## 2. 等级怎么登记：`ETModuleTiers`

| 想要 | 调什么 | 命中判据 |
|---|---|---|
| 某个**具体物品** = 第 N 档 | `ETModuleTiers.item(tier, vararg Supplier<out Item>)`（`ETModuleTiers.kt:61`） | `supplier.get() === stack.item`（`:107-112`） |
| **材料 + 形态** = 第 N 档 | `ETModuleTiers.prefix(tier, TagPrefix, vararg Material)`（`:75`） | 反查 `ChemicalHelper.getMaterialEntry(stack.item)` 后比形态 + 材料（`:125-132`） |
| **标签** = 第 N 档 | `ETModuleTiers.tag(tier, vararg TagKey<Item>)`（`:68`） | `stack.is(tag)`，父标签也算命中（`:95-97`） |
| 查等级 | `ETModuleTiers.tierOf(stack): Int`（`:83`） | 顺序固定 **物品 → tagprefix → 标签**，命中即返回，全不中返回 `0`（`:83-99`） |

能直接抄的登记片段（照 `ETModularTestMachine.kt:130-142`）：

```kotlin
companion object {
    // ⚠️ 登记动作发生在「机器注册期」：那时 GT 的物品还没进注册表，
    //    所以 ① 的入参必须是 Supplier（见 ETModuleTiers.kt:27-30）
    init {
        ETModuleTiers
            .item(1, Supplier { GTItems.ELECTRIC_MOTOR_LV.asItem() })  // ① 具体物品
            .prefix(1, TagPrefix.ingot, GTMaterials.Gold)              // ② 材料 + 形态
            .prefix(2, TagPrefix.ingot, GTMaterials.Titanium)
            .tag(1, CustomTags.LV_CIRCUITS)                            // ③ 标签
    }
}
```

⚠️ 四条硬规矩：

1. **等级必须 `> 0`**：`item` / `tag` / `prefix` 内部都会 `require(tier > 0)`
   （`:135-137`），登记成 0 直接抛 `IllegalArgumentException`（0 是「无模块 / 不合法」的保留值）；
2. **① 必须包 `Supplier`**，②③ 可以直接写：`GTMaterials.*` / `CustomTags.*` 在机器注册期已经可用
   （`:32-34` 的说明）；理由见 §7 坑 1；
3. **这张表是全局单例**（`:36-37`）：两台机器需要互相冲突的规则时，别往同一张表里塞，
   覆写 `tierOfModule`（`ETModularMachine.kt:54`）自己算；
4. tagprefix 那一支**只看登记过的形态**：只登记锭，金粉 / 金粒就不算模块
   （`ETModularTestMachine.kt:41-43`）。

## 3. 「第 N 档 = 第 N 套结构」是怎么落地的

三者的关系一句话：**`definition` 只存一套图案，运行时那套由 `getPattern()` 按当前档位现取**
（`ETModularTestMultiblocks.kt:17-20`）。

| 成员 | 关系 | 位置 |
|---|---|---|
| `patternOfTier(tier)` | 受保护的**抽象**方法，唯一的结构来源 | `ETModularMachine.kt:56` |
| `patternForTier(tier)` | 公开入口，实现体就是 `= patternOfTier(tier)` | `ETModularMachine.kt:62` |
| `getPattern()` | `= patternOfTier(moduleTier)`，结构检测走这条 | `ETModularMachine.kt:73` |
| `definition.pattern { }` | 只给**一套**（建议给最低档兜底，GTM 自动 DFS 预览也用它） | `ETModularTestMultiblocks.kt:42` |
| `definition.shapes` | 多页预览，**必须在 `register()` 之后**赋值 | `ETModularTestMultiblocks.kt:60` |

新增一套结构要改 **3 处**（以模块化测试机为例）：

| # | 改哪里 | 位置 |
|---|---|---|
| ① | `patternOfTier` 的档位→尺寸映射（建议按档位缓存图案，别每 tick 重建） | `ETModularTestMachine.kt:53` / `:66-67` / `:150-154` |
| ② | 预览页列表（`listOf(1, 2, 3)`） | `ETModularTestMachine.kt:179` |
| ③ | 模块规则（哪个物品/标签/形态是这一档） | `ETModularTestMachine.kt:130-142` |

### 3.1 非法档位：**没有契约**，调用方自己兜

- `patternForTier` 的 KDoc 明写「非法档位的表现由子类决定（可能抛异常），调用方自己兜」
  （`ETModularMachine.kt:58-61`）；
- 样例实现里**非法档位会被当成 3×3**：`sizeOfTier` 的 `else -> 3`（`ETModularTestMachine.kt:150-154`）；
  同一件事在终端规格里也写着（`README/zh_CN/高级终端行为规格.md:734`）；
- 终端的处理是**静默退回主结构**：`patternForTier` 外面包了 `try { } catch (Throwable) { }`，
  取不到就退回 `controller.getPattern()`（`AdvancedTerminalBuilder.java:129-146`）。

所以新写机器时：**想要的档位范围自己定死，越界要么抛（自己保证没人这么调）、要么给一个明确的兜底**，
别让它变成「玩家填 7 也搭出个 3×3 还以为是 bug」。

## 4. 线程：谁读、怎么读、作者要接什么

### 4.1 调用链（一句话：控制器 → 现扫部件表 → 线程仓的 `threadCount`）

| 环节 | 代码 | 位置 |
|---|---|---|
| 机器标记「我可以多线程」 | `interface IThreadedRecipeMachine : IMultiController`，两个成员**都有默认实现** | `IThreadedRecipeMachine.kt:27` / `:36` / `:54` |
| 现扫部件找线程仓 | `threadHatch`：遍历 `parts`，取 `part as? IThreadHatch ?: part.self() as? IThreadHatch`，**多个线程仓取 `threadCount` 最大的那个（不叠加）** | `IThreadedRecipeMachine.kt:36-46` |
| 线程数上限 | `threadCount = threadHatch?.threadCount ?: 1`（没装仓 = 1，退化回原版单配方） | `IThreadedRecipeMachine.kt:54` |
| 内核读上限 | `threadedMachine = machine as? IThreadedRecipeMachine`；`threadLimit = threadedMachine?.threadCount ?: 1` | `ThreadedRecipeLogic.kt:211` / `:242` |
| 部件声明 | `interface IThreadHatch { threadCount; maxThreads }` | `IThreadHatch.kt:31-48` |
| 部件实现 | `ThreadHatchPartMachine : TieredPartMachine, IFancyUIMachine, IThreadHatch` | `ThreadHatchPartMachine.kt:56-60` |
| 能力 | `ETPartAbility.THREAD_HATCH` | `ETPartAbility.kt:41` |
| 族与登记 | `ETThreadHatches.VARIANTS`（8 档）→ `.abilities(ETPartAbility.THREAD_HATCH)` → `ALLSmachine` | `ETThreadHatches.kt:124-133` / `:179` / `ALLSmachine.kt:27` |

### 4.2 要让一台机器支持线程，作者要做 5 件事

| # | 做什么 | 抄谁 |
|---|---|---|
| ① | `class X(holder) : WorkableElectricMultiblockMachine(holder), IThreadedRecipeMachine` | `TestMultiblockMachine.kt:59-62` |
| ② | 覆写 `createRecipeLogic`：`override fun createRecipeLogic(vararg args: Any?): RecipeLogic = ThreadedRecipeLogic(this)` | `TestMultiblockMachine.kt:70`（理由：GTM 的 `createRecipeLogic(Object...)` 是 `protected` 扩展点，不需要 mixin —— `TestMultiblockMachine.kt:33-46`） |
| ③ | 结构图案里**显式加线程仓的槽**：`Predicates.abilities(ETPartAbility.THREAD_HATCH).setMaxGlobalLimited(1).setPreviewCount(1)` | `ETTestMultiblocks.kt:80-83` |
| ④ | 配方修改器清单里**不要有并行修改器**（并行交给内核按线程施加） | `ETTestMultiblocks.kt:62-69`、契约见 `ThreadedRecipeLogic.kt:164-171` |
| ⑤ | （可选）面板追加线程行 | `TestMultiblockMachine.kt:88-92` → `ThreadedRecipeStatus.appendDisplayLines` |

**不用做的事**：Jade 那块是全局注册的、按 `recipeLogic is ThreadedRecipeLogic` 过滤
（`GTETJadePlugin.kt:40` / `:45`、`ThreadedRecipeLogicProvider.kt:216-219`），作者一行都不用写；
也不用碰任何 mixin。

```kotlin
class MyThreadedMachine(holder: IMachineBlockEntity) :
    WorkableElectricMultiblockMachine(holder), IThreadedRecipeMachine {

    override fun createRecipeLogic(vararg args: Any?): RecipeLogic = ThreadedRecipeLogic(this)

    override fun addDisplayText(textList: MutableList<Component>) {
        super.addDisplayText(textList)
        (recipeLogic as? ThreadedRecipeLogic)?.let { ThreadedRecipeStatus.appendDisplayLines(textList, it) }
```

### 4.3 线程 / 并行 / 超频**当前的真实关系**（照代码写，不美化）

| 维度 | 谁提供 | 内核怎么用 | 位置 |
|---|---|---|---|
| **线程数** | 线程仓 `IThreadHatch.threadCount`（玩家可下调，装上是上限全开） | 决定**同时能开几条线程槽**；槽位只增不减 | `IThreadedRecipeMachine.kt:36-46`、`ThreadedRecipeLogic.kt:736-748` |
| **并行倍数 M** | 并行仓（GTM 的 `IParallelHatch`，`getParallelHatch()` 只缓存一个实例） | **M 被重新定义成「每条线程」的并行上限**；整机上限 ≈ `线程数 × M` | `ThreadedRecipeLogic.kt:102-106` / `:613-646` / `:717-718` |
| **超频** | 机器自己的 `recipeModifiers`（例：`OC_NON_PERFECT_SUBTICK`、或超频仓那套 mixin） | 每开一条线程都先过一次 `machine.fullModifyRecipe(origin)`，所以**每条线程各自吃一遍超频** | `ThreadedRecipeLogic.kt:547-563`、`ETTestMultiblocks.kt:66-69` |
| **并行×超频** | — | 亚 tick / 批处理进的是 `subtickParallels` / `batchParallels`，**不是** `parallels`；`getTotalRuns() = parallels × subtickParallels × batchParallels` | `ThreadedRecipeLogic.kt:262-263` / `:649-657` |

⚠️ 三条「写代码时就会撞上」的口径：

1. **并行不许套两遍**：内核有一道防御 —— 传进来的配方 `parallels > 1` 就警告一次并不再叠加
   （`ThreadedRecipeLogic.kt:552-558` / `:570-579`）。所以**接了线程内核的机器，`recipeModifiers` 里不能有
   `PARALLEL_HATCH` 之类的并行修改器**；并行仓本身照旧要装（M 就是从它身上读的）。
   （顺带一条已核对的事实：GTM 自己的亚 tick 超频**不会**触发这条防御 ——
   `OverclockingLogic.OCResult.toModifier()` 把 OCResult 的第 4 个参数写进 `.subtickParallels(...)`，
   不是 `.parallels(...)`（GTM 7.5.3 字节码核对，无源码行号）。）
2. **多线程的「同配方 fan-out」是现状的一部分**：第一轮「不同配方各一条」，第二轮把空闲线程再发给
   已经在跑的同一种配方（`ThreadedRecipeLogic.kt:44-49` / `:471-502`），所以「线程条数 ≥ 配方种数」，
   整机同时处理次数会随线程数一起涨（`IThreadHatch.kt:8-14`）。
3. **客户端只有一个进度条**：线程表不是 `@DescSynced`，内核只把「下标最小的在跑线程」镜像进基类的
   `lastRecipe` / `progress` / `duration` / `isActive`（`ThreadedRecipeLogic.kt:765-777`）。
   整机状态走两条**服务端求值**的路（机器 UI 的 `ComponentPanelWidget`、Jade 的 `appendServerData`），
   客户端读 `runningThreadSlots` 永远是空表（`ThreadedRecipeLogic.kt:118-130`、
   `ThreadedRecipeStatus.kt:373-382`）。

### 4.4 ⚠️ 目前**没有**「模块化 + 线程」的现成合并类

| 事实 | 位置 |
|---|---|
| `ETModularMachine.createRecipeLogic` 固定返回 `ETModularRecipeLogic` | `ETModularMachine.kt:68` |
| `ETModularRecipeLogic` 是 Kotlin `class`（**final**），只做等级门禁 | `ETModularMachine.kt:119-128` |
| `ThreadedRecipeLogic` 也是 Kotlin `class`（**final**），只做线程调度 | `ThreadedRecipeLogic.kt:189` |
| `TestMultiblockMachine`（线程活样本）**不继承** `ETModularMachine` | `TestMultiblockMachine.kt:59-61` |

也就是说：想要「模块物品决定等级 **+** 多线程」的机器，现在没有能直接继承的类，
必须先改这两个类之一（把其中一个做成 `open` / 抽出可组合的 `matchRecipe` 覆盖），
或者新写一个继承 `ETModularMachine` 并实现 `IThreadedRecipeMachine` 的类**同时**再写一个
带等级门禁的线程逻辑子类。**这一条是读代码得出的结论，仓库里没有对应的说明或 TODO。**

| 两条例外 | 非 `IMultiController`（单方块机器）、`FusionReactorMachine`（EUt 语义特殊）都原样放行 | `MixinOverclockingLogic.java:182-188` |
| 算法 | `OverclockHatchHelper.modify(machine, recipe, maxVoltage, shouldParallel, logic)` → `OverclockingLogics.create(S, E)` → `SpecialOverclock.runOverclockingLogic` | `OverclockHatchHelper.kt:44-87`、`OverclockingLogics.kt:43-45` / `:50-83` |
| 算法语义 | 每级 `duration × (1/S)`、`EUt × (E×S)`；先判电（超 `maxVoltage` 停）再判时间（不足 1 tick 整级作废）；`OCResult(..., parallels = 1)` —— 超频仓**不碰并行** | `OverclockingLogics.kt:63-82` |
| 结构里可插 | `autoAbilities(checkMaintenance, checkMuffler, checkParallel = true)` 上追加 `OVERCLOCK_HATCH`，与并行仓同规格 `maxGlobalLimited(1)` | `MixinPredicatesAutoAbilities.java:55-74`（`setMaxGlobalLimited(1)` 在 `:70-71`） |

⚠️ 一台机器**只认一个**超频仓（`getParts()` 里找到第一个就 `return`，`MixinOverclockingLogic.java:190-196`），
结构里通常也只允许 1 个（`MixinPredicatesAutoAbilities.java:69-71`）。

### 5.2 要加「时间流消耗」的话：能挂的只有这几处

| 想改哪一层 | 落点 | 拿得到什么 / 拿不到什么 |
|---|---|---|
| **每级超频消耗多少时间流** | `OverclockingLogics.SpecialOverclock.runOverclockingLogic`（`OverclockingLogics.kt:50-83`） | ✅ 唯一知道「**实际生效了几级**超频」的地方（循环里的 `ocLevel`，`:74`），也是唯一知道每级乘数的地方；❌ 拿不到「这台机器/这个方块坐标」以外的上下文（只有 `OCParams` 与 `maxVoltage`） |
| **要在超频前后做全局记账（扣时间流 / 不足就退回标准超频）** | `OverclockHatchHelper.modify`（`OverclockHatchHelper.kt:44-87`） | ✅ 拿得到 `machine` / `recipe` / `maxVoltage` / `hatch`（部件已在 `MixinOverclockingLogic.java:190-194` 解出 S 与 E）；❌ 拿不到最终 `ocLevel` —— 它返回的是 `ModifierFunction`，想知道实际级数得看 OCResult（`:86`） |
| **想让「没有超频仓」的机器也吃时间流** | 得进 `OverclockingLogic` 接口的 default 方法 | ❌ **做不到**：Mixin 0.8.5 的注解处理器对「mixin 本身是接口」直接报 `Injector in interface is unsupported`（`MixinOverclockingLogic.java:24-35` 有原始报错文本），只能继续往 `GTRecipeModifiers` 的调用点加 `@Redirect` |

⚠️ 全仓 `grep` 搜「时间流 / 时流 / TimeFlux / TF」**零命中**：时间流目前只有设定文档、
没有任何代码或类，所以上面给的是**挂点**而不是现成 API —— 别照着还不存在的类名写代码。

## 6. 部件能力怎么声明（`ETPartAbility` / `MachineDefinition#abilities`）

| 要做什么 | 写法 | 位置 |
|---|---|---|
| 新建一种能力 | `val X: PartAbility = PartAbility("gtet_xxx")`（构造函数就是 public，**没有全局注册表**） | `ETPartAbility.kt:22-41`；GTM 侧 `PartAbility.java:67-69`（05 §5） |
| 把方块登记进能力 | 注册链上 `.abilities(ETPartAbility.X)` | `ETThreadHatches.kt:179`、`ETOverclockHatches.kt:196`、`MachineBuilder.java:519`（05 §1） |
| 登记发生在什么时候 | 方块注册回调里 `ability.register(tier, block)` | `MachineBuilder.java:778`（05 §1）→ 所以 `.tier(...)` 必须在 `.register()` 之前 |
| 结构里认这个能力 | `Predicates.abilities(能力).setMaxGlobalLimited(1).setPreviewCount(1)` | `ETTestMultiblocks.kt:80-83`、`Predicates.java:134`（05 §2） |
| 不让部件共享 | `override fun canShared(): Boolean = false` | `ThreadHatchPartMachine.kt:146`、`IMultiPart.java:27-29`（05 §5，GTM 默认 `true`） |

⚠️ 三个坑（都是仓库里写明 / 已踩过的）：

1. **能力按对象身份区分，名字只用于调试**（`ETPartAbility.kt:24-28`）。别的 mod 自己
   `PartAbility("gtet_thread_hatch")` **不是**本仓的 `ETPartAbility.THREAD_HATCH`：
   两边结构互不认，而且不报错。跨 mod 想共用能力，只能共用**同一个对象**。
2. **能力方块表是首取即定的快照**：`PartAbility#getAllBlocks()` 由 `GTMemoizer.memoize` 缓存
   （`PartAbility.java:61-62`，05 §1 的 ⚠️），所以**先注册仓、再注册用到它的多方块**是硬顺序，
   本仓落在 `MachineRegister.kt:5-6`（先 `ALLSmachine` 后 `ALLMmachine`）。
3. **能力对象本身不会让任何结构接受部件**：部件 `.abilities(...)` 只回答「它属于哪个能力」，
   结构接受谁由结构自己的谓词说了算（`MixinPredicatesAutoAbilities.java:30-39`）。
   这正是「线程仓为什么不进那条 mixin」的理由：进 mixin 等于对所有 `autoAbilities(_, _, true)`
   的机器（含 GTM / GCYM）生效，那些机器不实现 `IThreadedRecipeMachine`，
   插上去就是**能插但不生效**的装饰件 —— 所以线程仓由 GTET 自己的多方块在机壳谓词上显式加槽。

## 7. 常见坑（每条都有仓库内出处）

| # | 坑 | 出处 |
|---|---|---|
| 1 | **注册期读不到物品注册表**：机器注册时就访问了机器类，而 GTM 是 `GTMachines.init()` 早于 `GTItems.init()`（字节码核对：`CommonProxy.init()` 里 `GTMachines.init` → `GTFoods.init` → `GTItems.init`，无源码行号），此时写 `GTItems.X.asItem()` 会抛 `Registry entry not present` | `ETModularTestMachine.kt:124-128`、`ETModuleTiers.kt:27-30`（→ ① 用 `Supplier`） |
| 2 | **`companion object` 的 `init` 会被编进外层类的 `<clinit>`**，所以「在 `companion` 里登记」= 「在类首次加载（= 机器注册）时执行」，不是「运行时才执行」 | `ETModuleTiers.kt:27-28`、`ETModularTestMachine.kt:124-126` |
| 3 | **等级登记成 `0` 会静默不成型**（`0` 是保留值），所以 `require(tier > 0)` 直接抛出来更安全 | `ETModuleTiers.kt:134-137`、`ETModularMachine.kt:26-28` |
| 4 | **tagprefix 反查必须先判 `entry.isEmpty`**：查不到时 GTM 给的是 `NULL_ENTRY`（形态 `NULL_PREFIX`、材料 `GTMaterials.NULL`），不判就会拿「空形态」查表 | `ETModuleTiers.kt:117-131` |
| 5 | **别用 `ItemStack#getTags()` 遍历标签**：它返回 Java `Stream`，Kotlin 里没法 non-local `return`；规则表通常只有几条，按登记顺序 `is` 一遍最省事 | `ETModuleTiers.kt:92-97` |
| 6 | **`patternForTier` 对非法档位没有契约**，样例实现里非法档位 = 3×3；终端只能静默退回主结构（不报错） | `ETModularMachine.kt:58-61`、`ETModularTestMachine.kt:150-154`、`AdvancedTerminalBuilder.java:129-141`、`README/zh_CN/高级终端行为规格.md:734` |
| 7 | **`getPattern()` 在 0 档也会被调**（终端那条兜底路径），所以 `patternOfTier(0)` 别抛；终端对这次调用包了 try/catch，抛了就是「这次搭建什么都不做」 | `ETModularMachine.kt:73`、`AdvancedTerminalBuilder.java:142-146` |
| 8 | **预览页的 `repetition` 数组长度必须等于图案的 aisle 条数**，传空数组 = `BlockPattern.getPreview` 立刻 AIOOBE；本项目真踩过，后果是「整台机器没有预览 + 把 gtceu 那一整批 EMI 注册一起带走」 | `ETModularTestMachine.kt:165-176`、05 §3（实测栈） |
| 9 | **`definition.shapes` 必须在 `register()` 之后赋值**：builder 阶段还没有 definition 对象 | `ETModularTestMultiblocks.kt:58-60` |
| 10 | **`@Persisted` 字段读档后的夹取只能写在机器类自己的 `loadCustomPersistedData`**（写在 trait 里收不到那次调用），且必须先 `super` | `ThreadHatchPartMachine.kt:126-142`、05 §5 的调用链 |
| 11 | **接了线程内核的机器，`recipeModifiers` 里不能有并行修改器**（否则并行²）；内核只警告一次、不再叠加 | `ThreadedRecipeLogic.kt:164-171` / `:552-558`、`ETTestMultiblocks.kt:62-69` |
| 12 | **线程表不进同步**：客户端读 `runningThreadSlots` 永远是空表，只能在**服务端**求值（机器 UI 的 `textSupplier`、Jade 的 `appendServerData`） | `ThreadedRecipeLogic.kt:118-130` / `:250-259`、`ThreadedRecipeStatus.kt:379-382` |
| 13 | **玩家下调线程数不会砍掉已在跑的线程**（砍掉等于吞料），只是不再开新线程 | `ThreadHatchPartMachine.kt:39-43`、`ThreadedRecipeLogic.kt:736-748` |
| 14 | **每 tick `machine.onWorking()` 只调一次**（不是每条线程一次），所以「某条线程的独立失败」没法通过这个钩子表达 | `ThreadedRecipeLogic.kt:344-346` / `:145-146` |
| 15 | **超频挂钩只能选 `@Redirect` 调用点**：往 `OverclockingLogic` 接口的 default 方法注入会被 Mixin AP 拒（`Injector in interface is unsupported`），5 个调用点必须全部重定向，漏一个就是「能插仓但没效果」 | `MixinOverclockingLogic.java:24-35` / `:50-54` / `:68-69` |
| 16 | **`OverclockHatchHelper` 里那段「自己算 OCs」不是洁癖**：它不能回头调 `logic.getModifier(...)`（否则重新进入注入点）；且它有意把 GTM 的 `OCs == 0` 收紧成 `OCs <= 0` | `OverclockHatchHelper.kt:18-28` / `:63` |
