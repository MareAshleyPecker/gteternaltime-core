# 机器渲染工作室（Studio）· 设定与规划

> 状态：**想法已定稿，尚未开工**（本文件是设计文档，按仓库口径**不入公开仓库**）。
> 目标环境：Forge 1.20.1 + GTCEu/GTM 7.5.3 + LDLib（本仓 `GTEternalTime -- core`）。
> 第一个真实用例：**ETV 那台机器要渲染一个巨大的镂空时钟**（指针要动）。
> 节奏：**慢慢做**，不排期；按里程碑逐个验收，上一个不过不进下一个。

---

## 1. 一句话

**在游戏里、在世界里、用鼠标直接给多方块机器做模型与特效**；三种编辑范式
（BB 体素 / Blender 网格 / 中望 3D 风格 CAD）**共享同一个几何内核与同一份数据格式**；
整个功能收在一个包内，**以后可以整包抽出去当独立库**。

---

## 2. 已定决策（用户拍板，勿再反复）

| # | 项 | 结论 |
|---|---|---|
| 1 | 形态 | **游戏内编辑器**（不是独立桌面程序）。理由：预览必须在真实环境里——真实光照、真实遮挡、真实光影包、真实帧率。 |
| 2 | 编辑位置 | **直接在世界里改**（Axiom 式）：gizmo、热键、无需开窗口。GUI 窗口只作兜底（数值输入、层级树、时间轴）。 |
| 3 | 导入 | **多格式都要**：OBJ(+MTL)、Blockbench 导出、glTF（可选）⇒ 导入器必须是**可插拔**的一层。 |
| 4 | 动画 | **在工具里自定义**：关键帧/曲线/时间轴，不是只有匀速转。 |
| 5 | 范式 | **可切换三种**：BB 风格、Blender 风格、**中望 3D 风格（CAD）**。 |
| 6 | 落地 | 本 mod 里**单开一个包**，所有逻辑都在包内，方便整包抽出打包。 |
| 7 | ZW3D/CAD | **写进计划**（见 §6 / §9），不是砍掉；但只做子集，见 §6 的 A/B/C 分级。 |
| 8 | 节奏 | 慢慢做，先把想法与格式定死，再动手。 |
| 9 | 世界内编辑的实现路线 | **全自研**（`interaction/` 自己写）。**WorldEdit 不作为底座**——它没有 UI、学习成本换不回收益，详见 §6.1。 |

## 3. 架构分层（"能抽出去"是设计约束，不是愿望）

```
        ┌──────────── 交互层（做一次，三范式共用）────────────┐
        │  世界内射线拾取 · gizmo 手柄 · 轴锁定/吸附 · 撤销栈   │
        └──────┬──────────────┬───────────────┬──────────────┘
          BB 模式 │   Blender 模式 │   CAD（中望）模式
        （体素）  │  （顶点/边/面）│  （图元/布尔/参数）
        └───────┴───────┬───────┴───────────────┘
                 ┌───────▼────────┐
                 │   几何内核      │  纯 Kotlin：网格 · 图元 · 布尔/SDF · 体素化 · 动画求值
                 └───────┬────────┘
                 ┌───────▼────────┐
                 │  数据格式(JSON) │  三范式写同一份数据，可版本迁移
                 └────────────────┘
```

### 包结构

```
rain/gtetcore/gtet/studio/
├── api/          对外稳定接口：StudioModel / StudioPart / StudioMaterial / StudioClip / StudioRuntime / StudioHost
├── kernel/       ★ 纯几何与动画求值（Mesh / Primitive / Csg / Sdf / Voxelize / Curve）
├── data/         JSON 数据模型 + 序列化 + 热重载 + 版本迁移
├── format/       可插拔导入导出：StudioFormat(interface) + ObjFormat / BlockbenchFormat / GltfFormat
├── render/       VBO 缓存 · RenderType · 光照 · 材质解析
├── interaction/  世界内交互：射线拾取 · gizmo · 吸附 · 撤销栈（命令模式）
├── editor/       三种范式各自的编辑逻辑（bb / blender / cad 三套工具集）
└── integration/  ★ 唯一允许 import GTM 的地方：DynamicRender 包装、机器状态源
```

**依赖纪律（最重要的一条，2026-09-30 按实测修订）**：
- **`kernel / format / config` 一行都不许依赖 Minecraft**（这三个是真正的"库内核"，要能**脱机单测**；
  实测它们连 Forge 都不 import）；
- `api / data / render / editor / interaction` **可以用 MC / Forge / LDLib**（加载资源、磁盘纹理、
  绘制与输入本来就离不开它们）；
- **只有 `integration/` 认识 GTM**，且它是唯一的宿主接线点。
- 需要问宿主要东西（"这台机器现在在干什么"）时走 `StudioHost` / `StudioTargetSource` 这类**窄接口**，
  由 `integration/` 实现。

> ⚠️ 修订说明：原规则写的是"`kernel / data / format` 不许依赖 MC"，**实现与它对不上**——
> 实测 `data/` 有 11 处 MC import + 2 处 Forge（`FMLPaths`、磁盘纹理的 `NativeImage` 等），
> 那是"从磁盘读资源、注册纹理"必需的。硬要抽掉只会多一层无谓间接。
> ⇒ 定为：**可脱机测的那三个子包保持零 MC**，其余允许；抽取时的真正成本只有 GTM 与 modid 常量（见 §3.1 末）。

## 4. 数据格式（草案，是整个工具的命脉）

**产物是数据，不是代码**——否则改个参数就要重编译，工具就退化成一个代码脚手架。

```jsonc
{
  "version": 1,
  "id": "gtet:etv_clock",
  "kernel": "hybrid",                     // mesh | voxel | cad | hybrid
  "sources": [                            // 导入来源（导入后可继续参数化编辑）
    { "format": "obj", "path": "gtetcore:models/machine/etv_clock.obj", "scale": 1.0 }
  ],
  "materials": {
    "frame": { "texture": "gtetcore:block/machine/etv_clock", "render": "cutout", "cull": false },
    "glow":  { "texture": "gtetcore:block/machine/etv_clock_glow",
               "render": "translucent", "blend": "add", "light": "fullbright", "color": "#FFD080" }
  },
  "parts": [                              // 层级 + 变换 + 轴心；merge=true 的部件烘进静态 VBO
    { "name": "body",   "material": "frame" },
    { "name": "hour",   "material": "frame", "parent": "body", "pivot": [0, 32, 0], "merge": true },
    { "name": "minute", "material": "glow",  "parent": "body", "pivot": [0, 32, 0] }
  ],
  "features": [                           // ★ CAD 模式的参数化历史（可重算，改尺寸即重建）
    { "type": "cylinder", "name": "dial", "params": { "r": 12, "h": 1, "seg": 64 } },
    { "type": "array",    "name": "spokes", "of": "spoke", "count": 12, "axis": "z", "radius": 10 },
    { "type": "boolean",  "op": "subtract", "a": "dial", "b": "spokes" }
  ],
  "anchor":  { "mode": "machine", "face": "front", "offset": [0, 1, 0] },
  "bounds":  { "min": [-16, 0, -16], "max": [16, 64, 16] },
  "animation": {
    "driver": "gameTime",                 // gameTime | machine.progress | machine.timeFlow | machine.formed
    "tracks": [
      { "part": "hour",   "channel": "rot", "axis": "z",
        "keys": [{ "t": 0, "v": 0 }, { "t": 72000, "v": 360 }], "loop": "wrap", "easing": "linear" },
      { "part": "minute", "channel": "rot", "axis": "z",
        "keys": [{ "t": 0, "v": 0 }, { "t": 6000,  "v": 360 }], "loop": "wrap", "easing": "linear" }
    ]
  }
}
```

- 文件放 `config/gtetstudio/`（路径待定），**文件改动即热重载**，不用重启游戏。
- `version` + 迁移函数：格式一定会变，第一次就要留迁移口子。
- `driver` 现在只实现 `gameTime`，其余是**预留枚举**，加一个枚举就能接机器状态。

### 4.1 从 CAD 的文件组织里抄四条（2026-09-30 追加）

参考中望 3D 那类 CAD 的做法（其文件分**零件 / 装配体 / 工程图**，
核心是**历史树**，另有**封装/记录状态**与**文件打包**等操作）：

| CAD 的做法 | 我们的对应做法 |
|---|---|
| **存配方（参数化历史）而不是只存结果**——历史树才是本体 | `features` 字段就是这件事：存"圆柱 r=12 → 阵列 12 → 布尔减"，**不存烘好的网格** |
| **结果与显示缓存分开**：打开时先用三角化缓存秒显示，再按需重算 | 布尔很贵 ⇒ **算完要落一份网格缓存**，下次先显示缓存、按需重算。否则 M3 一做布尔，每次启动都要重算一遍 |
| **外部参照 + 打包**：装配只存"引用 + 实例位姿 + 约束"，所以才有"文件打包" | M1a 刚支持**磁盘 OBJ/贴图** ⇒ 立刻会遇到"模型还在、贴图被挪走"。需要**依赖检查 / 打包**（载入时报缺哪些文件；`/gtetstudio pack` 收集依赖） |
| **封装 / 记录当前状态**（把历史冻结固化） | 对应**"烘焙成静态网格"**：调好的 CAD 模型冻结后不再重算、只画静态 VBO——性能友好，也防误改 |

⚠️ **边界**：**不引入 B-rep / NURBS 内核**。"改个尺寸就全联动重算"背后是曲面求交内核（数年量级），
我们的 CAD 只做 §5 的 **A 级子集（图元 + 布尔 + 参数）**，用**体素/SDF 或网格布尔**实现——
对"圆 + 阵列 + 布尔减"这类零件完全够用，而存储上照样享受"存配方"的全部好处。

## 5. 三种编辑范式（各自要什么、成本多少、排在哪）

| 范式 | 编辑对象 | 内核要求 | 成本 | 里程碑 | 对"镂空时钟" |
|---|---|---|---|---|---|
| **BB 体素** | 立方体（吸附到格） + 每面 UV/调色板 | 体素网格 + 面材质分配 | **便宜**（bb 的模型本质就是"一堆立方体 + 每面贴图"） | M5 | 能做粗齿轮与表盘，做不了细指针弧线 |
| **Blender 网格** | 顶点 / 边 / 面：挤出、环切、法线 | 半边形数据结构 + 屏幕空间拾取 | **中偏贵** | M6 | 什么都能做，但在游戏里拉顶点很累 |
| **中望 3D（CAD）** | 图元 + 布尔 + **尺寸参数** | 图元建模 + 稳健布尔（+ 可选的约束求解） | **最贵** | **M3（子集）/ M7（完整）** | ★ **最合适**：时钟就是"圆 + 阵列 + 布尔减" |

### CAD 那一路的分级（写进计划，按能力递进）

- **A（推荐，M3）**：图元（盒/柱/球/环/阵列）+ **布尔** + **尺寸参数**，无草图约束。
  —— 时钟的全部零件（表盘环、辐条、指针、齿轮）都能做出来，且**改一个数字整个模型重建**，
  这已经拿到中望 3D 八成的爽感，成本只有零头。
- **B（远期）**：再加**草图**（画 2D 轮廓）→ 拉伸 / 旋转。造型自由度跳一级，
  但要做轮廓闭合检查、拉伸/旋转成体算法。
- **C（长期，默认不做）**：完整参数化（尺寸约束 + 几何约束 + 改一处全联动）。
  这等于**重写一个 CAD 约束求解器**，是独立课题，明确列为长期/不做，除非以后真需要。

## 6. 世界内编辑（Axiom 式）的技术清单

**渲染 gizmo 反而是最简单的部分**（自己画线/箭头，走 `RenderLevelStageEvent` 即可）。
真正的成本在这三件，而且 **LDLib 一件都不提供**：

| 要做的 | 为什么难 | 备注 |
|---|---|---|
| **世界内拾取** | 鼠标位置 → 世界射线，与"gizmo 手柄 / 部件包围盒 / 顶点"求交；命中优先级要处理（先手柄、再顶点、再部件） | 交互层做一次，三范式共用 |
| **拖拽语义** | 轴锁定、平面锁定、网格吸附（0.25/1 格）、临时翻转键 | 手感全在这里，最容易做成"能用但难用" |
| **撤销栈** | 每次拖拽是一个**原子操作**；连续拖拽要合并成一条 | **必须一开始就用命令模式**（每个编辑动作 = 可逆 Command），不能事后补 |

**取舍**：GUI 窗口降级为兜底（数值输入永远要有、层级树与时间轴放窗口里），
主力交互是**世界内 gizmo**——Axiom 那种"不用开窗口"的爽感就来自这个取舍。

### 6.0 编辑器模式：**独占输入**（2026-09-30 实机后定案）

M2a 第一版是"**和原版抢输入**"（监听 Forge 的 `InputEvent`、在世界里边玩边拖）。**实机证明这条路走不通**：

| 事实 | 数字 |
|---|---|
| 轴手柄的命中半径 | `0.07 × 轴长`，样例轴长 ≈0.59 格 ⇒ **≈0.041 格** |
| 在 3.7 格距离、1080p 下折算 | **屏幕上约 8 像素** |
| 而原版**锁着鼠标**（光标钉在窗口中心，移动鼠标是转视角） | 唯一指针是准星 ⇒ 用准星戳一条 8 像素宽、还随转头移动的轴，**做不到** |

⇒ 定案：**做一个独占输入的"编辑器模式"**（与 Axiom 的 Editor Mode 同一思路）：
打开一个**不暂停**的 `Screen`，它天然会 `releaseMouse()`（光标解锁）并吃掉全部鼠标/键盘事件，
于是**原版操作被整体屏蔽**（不挖方块、不用物品、不切物品栏、玩家不自走）。

- **相机**：Screen 吃掉键盘后玩家动不了 ⇒ 编辑器自己实现飞行（WASD + 空格/Shift）与右键转视角；
  这就是"像 Unity/Blender 的视口"的那部分。
- **修饰键可绑定 + 拖拽期间不飞行**（2026-10-01 实机反馈后追加）：两个吸附修饰键
  （默认 `Ctrl`=整格吸附 / `Shift`=精细不吸附）注册成 `KeyMapping`，在 选项→控制→按键绑定→「机器渲染工作室」里可改，
  `StudioInteractionEvents.currentSnapRule()` 跟着变（不再写死 GLFW 键码）；
  同时**拖拽 gizmo 期间停掉飞行轮询** —— 否则"按住 `Shift` 精细拖"会变成"一边拖一边往下掉"。
  读键走 GLFW（理由见 §10.1 那条 `KeyMapping.isDown()` 结论）。
- **拾取**：光标解锁后 `mouseHandler.xpos()/ypos()` 就是**真实鼠标位置**，8 像素的轴才真的能戳中。
- **面板**：M2b 先用原版 `GuiGraphics` 画最小面板（工具条 + 状态 + 提示），**不引入 LDLib**。
- ⚠️ 两个连带细节：① `drawGizmo` 里原来那句 `if (mc.screen != null) return` **必须改成只挡别人的界面**，
  否则编辑器一开 gizmo 就没了；② Esc 要自己接管（拖拽中=取消拖拽，否则=退出编辑），
  **不能**走成原版 `onClose` 弹暂停菜单——M2a 那个"200ms 窗口内关掉 PauseScreen"的补丁随之作废。


### 6.1 已否决：WorldEdit 不作为底座（2026-09-30 定）

`libs/` 里放过 `worldedit-7.2.15.jar` 与 `WorldEditCUI-1.20.1.jar`，评估过"拿它当世界内编辑的底座"，
**结论：不用**。理由：

1. **它没有 UI** —— WorldEdit 是命令 + 选区 + 方块操作引擎，Axiom 那套好看的编辑体验是
   **Axiom 自己写的**，不是 WE 给的。用它只买到"撤销栈 / 选区 / CUI 协议"三件底层零件，
   而**真正的工作量（gizmo、拖拽语义、面板、预览）一件都省不掉**。
2. **学习成本换不回收益** —— 我们的编辑对象是**模型部件（几何）**，不是世界方块；
   套 WE 的 `EditSession` / `Extent` 模型反而要把"几何编辑"硬弯成"方块事务"，
   学一套不贴合的 API，比自研那三件零件更慢。
3. **许可证**（否决后的附带结论）：WorldEdit 是 **GPL-3.0**，本来也只能运行时依赖、
   **绝不能 jarjar 内嵌**（内嵌会要求整个 mod 也 GPL）。

⇒ **M2 全自研**：`interaction/` 自己写射线拾取、gizmo、吸附、命令模式撤销栈。
   好消息是这三件都在我们自己的坐标系里（模型局部空间），比"跟世界方块打交道"简单得多。

> （若以后确实需要"把模型贴着世界方块操作"，再单独评估；不作为当前路线。）

## 7. 渲染与性能要点

1. **导入时按部件切分，每个部件一个 VBO**；`merge: true` 的静态部件合并成一张
   ⇒ **静态部分一次 draw call**（镂空模型三角形多，这条是能不能扛住的关键）。
2. 运行时只算**层级变换矩阵**，**绝不重新上传顶点**
   （反面教材：GTLAdditions 的敌基督光束每帧 CPU 现拼几何再上传）。
3. **镂空必开双面**（`cull = false`）——不然从内部看整片面消失，镂空结构最容易露馅；
   边缘用 **cutout（alpha 剪裁）**而不是 translucent，省掉深度排序。
4. 光照：静态部件按机器位置采样 `packedLight`（`.uv2(...)`）；`glow` 材质走全亮。
5. **包围盒与视距必须自己管**（GTM 的 `getRenderBoundingBox` / `shouldRenderOffScreen` /
   `getViewDistance`）——大时钟远超一个方块，否则会被区块剔除切掉半截。
   ⚠️ 两个反直觉点（侦察实测）：① `getRenderBoundingBox` **只喂视锥剔除、不裁三角片**，
   但它默认只有"方块 ±1"，**不 override 就等于没有**；② **`shouldRenderOffScreen` 不是"无视视锥"**，
   它只是把 BE 放进 `globalBlockEntities`（渲染时照样过视锥），救不了"控制器出视锥整台消失"。
   ⇒ 唯一有效的做法是**把 AABB 放大到能把整个模型包住**（参考 GTM `FusionRingRender` 的 `inflate(viewDistance/2)`）。
6. 不活跃就不渲染（机器没成型 / 没在工作时早退）。
7. **静态大件照抄 GTM 的现成实现**：`MultiblockInWorldPreviewRenderer` 把整个结构烘进
   `VertexBuffer[]`，每帧只 `bind + drawWithShader`——我们的 `merge` 部件用它，指针则每帧现画。
8. **预览相关**：编辑器窗口的 3D 视口可直接复用 LDLib `SceneWidget` + 覆写 `renderBeforeBatchEnd`；
   ⚠️ **绝不能调 `useCacheBuffer()`**（它内部无条件 `useCache = true`，会把旋转的指针烘死）。

### 7.1 渲染上限与降级（2026-09-30 追加 —— **必须做，不是可选**）

**为什么要一开始就有**：模型是**数据**，玩家/我们自己往 `config/gtetstudio/` 里丢什么都有可能；
而 `DynamicRender.render` 是**每台机器各调一次**的 ⇒ 屏幕上有 N 台就 N 遍提交。
没有上限时，一个 50 万面的模型 + 十台机器就能把客户端拖死，而且**看起来像"mod 有 bug"**。

**上限的度量单位统一用「三角形数」**（最直观；显存实际由 顶点数 × 顶点格式 决定，用三角形数近似即可）。

| 配置项 | 默认 | 语义 | 超限时怎么办 | 落在哪一步 |
|---|---|---|---|---|
| `enabled` | `true` | 总开关：关掉后**一台都不画**（排查"是不是 studio 拖的"时用） | —— | M1a |
| `maxTrianglesPerModel` | `200000` | **单模型**三角形上限，**载入期**校验 | **拒绝载入**并明确报错（说明是哪个文件、多少面、上限多少）；**不是**静默削面 | M1a |
| `viewDistance` | `256` | 每模型视距（JSON 里可 per-model 覆盖） | 超出不画（交给 `shouldRender`） | M1a |
| `maxVisibleModels` | `16` | **同屏**同时渲染的 studio 模型数 | 按**距相机距离由近到远**保留前 N 个，其余本帧不画；**日志/调试面板要能看出"因超限未渲染 N 个"** | M5 |
| `maxTotalTriangles` | `800000` | 所有可见模型的**三角形总预算** | 同样按距离从远到近停画（近处优先） | M5 |
| `animationMaxDistance` | `64` | 超过这个距离**降级** | 只画 `merge` 的静态部分，**不更新也不画动态部件**（远端看不出指针在转，但省掉每帧现画的几何） | M5 |

**三条纪律**：

1. **超限行为必须是确定的、可观测的**：谁被丢掉（按距离排序）、丢了多少，都要能在日志/调试面板里看见——
   否则以后看到"机器没画出来"会以为是渲染器坏了，实际是撞了上限。
2. **载入期拒绝 ≠ 运行期丢帧**：`maxTrianglesPerModel` 是**载入时**就把坏模型挡在门外（防呆、报错清楚）；
   同屏数量与总预算才是**运行期**的降级。两者不要混在一起做。
3. **配置属于 studio 包自己**（`studio/config/StudioConfig.kt`，用 `ForgeConfigSpec`）——
   **不许挂到 `GTETConfig.java` 上**，否则整包抽出去时会把宿主 mod 的配置一起拖走。

> 默认值取"顺手就能用、但明显挡住灾难"的量级：20 万面单模型 ≈ 一个相当精细的机械模型；
> 800000 总预算 ≈ 同屏四五个大件。以后按实机表现再调，**但开关必须先在**。

## 8. 里程碑路线（每步都能单独验收）

| | 阶段 | 产出 | 验收标准 |
|---|---|---|---|
| **M0** | 数据格式 + 运行时绘制 | 手写 JSON，把模型画在机器上并转起来（**不做任何 UI**） | 时钟出现在 ETV 机器上，位置/朝向/光照正确 |
| **M1** | 导入器（可插拔） | OBJ(+MTL) / Blockbench 导入 → 生成 JSON | Blender 里做的时钟能直接用 |
| **M2** | **世界内交互层** | 射线拾取 + 移动/旋转/缩放 gizmo + 吸附 + 撤销栈 | 在世界里拖得动、能撤销，手感可用 |
| **M3** | **CAD 模式（子集 A）** | 图元 + 布尔 + 参数化尺寸 | 做出镂空表盘，改参数能重建 |
| **M4** | 动画时间轴 | 关键帧、插值曲线、播放预览 | 时钟按设定速度转，随时改随时看 |
| **M5** | BB 模式 | 体素编辑 + 每面贴图 | 能在游戏里搭一个方块风零件 |
| **M6** | Blender 模式 | 顶点/边/面编辑（**独立网格内核**） | 能拉顶点微调造型 |
| **M7** | 完整 CAD（长期） | 草图 + 约束求解 | 非必需，视需要再决定 |

**顺序理由**：M2 是三种范式共用的地基，先做它；之后每加一个范式都是"接上手柄"，
而不是"再写一个编辑器"。M3 在三种范式里排最前，因为它对**现在唯一的需求（镂空时钟）最直接**。

> **导入格式的现实**（侦察结论）：**OBJ(+MTL) 是唯一"开箱即用"的格式**（Forge `forge:obj` 原生支持）；
> 原版 JSON 模型走原版管线；**Blockbench 导出与 glTF 需要我们自己写解析器**（在 `format/` 里做成可插拔）。
> ⇒ M1 先做 OBJ（够用且零成本），Blockbench/glTF 按需再加。

## 9. 风险与已知深坑

1. **薄壁布尔**：镂空 = 大量薄壁，而薄壁正是**网格布尔（BSP/mesh boolean）最容易翻车**的地方
   （自交、碎面、法线乱）。⇒ **优先体素/SDF 内核**（布尔 = `min/max`，永不失败），
   或做**双内核**（体素/SDF 负责 CSG 与镂空，自由网格负责造型，**单向转换**：网格→体素可以，反过来不行）。
2. **一上来做三个范式 = 同时做三个工具**，必然烂尾。⇒ 严格按 §8 顺序，范式一个一个加。
3. **游戏内拖顶点很累**：所以 BB 与 CAD 优先于自由网格编辑——它们把"操作的单位"变大了。
4. **撤销栈不能事后补**：一开始就命令模式。
5. **内核必须不依赖 MC**，否则抽不出去、也没法单测。
6. **大型模型的剔除与光影**（见 §7）——这是"能不能用"而不是"好不好看"的问题。

## 10. 技术底座核实结论（2026-09-30 侦察，全部有证据）

### 10.1 已核实（结论 → 证据）

| 问题 | 结论 | 证据 |
|---|---|---|
| LDLib 能不能直接吃 OBJ | **不能**：LDLib 1.0.50 **没有任何自有 3D 模型解析器**（OBJ/glTF/FBX 一个都没有），它只包原版 JSON 管线（`IModelRenderer` → `ModelFactory` → 原版 `ModelBakery`） | LDLib jar 全表 grep `OBJ/Gltf/FBX` 只命中 `*Object*` 子串 |
| 那模型从哪来 | **Forge 的 `forge:obj`**：`ObjLoader.loadModel(ModelSettings)` → `ObjModel`；**OBJ(+MTL) 走它，原版 JSON 走原版，glTF/FBX 必须自己写解析** | `ObjLoader.java:48/64/81`、`ObjModel.java:497/665` |
| **分部件转指针有没有官方解法** | **有，而且正好命中需求**：`ObjModel.bakeRenderable(ctx)` → `CompositeRenderable`，用 `Transforms.of(ImmutableMap<String, Matrix4f>)` **按 OBJ 的 `g`/`o` 组名给单个部件单独叠矩阵** | `CompositeRenderable.java:35/158/163/176`，`PartBuilder.child():129` |
| GTM 7.5.3 怎么挂 | **不在 `MachineBuilder`**，在 `MachineModelBuilder#addDynamicRenderer(Supplier<DynamicRender>)`，经 `.model(...andThen { it.addDynamicRenderer { ... } })` 接；**且必须同时 `DynamicRenderManager.register(id, TYPE)`**（否则 datagen/加载报 "type does not exist"），还要 `.hasBER(true)` | `MachineModelBuilder.java:173`、GTM 真实用例 `GTMachineUtils.java:547-558`、`DynamicRenderManager.java:39` |
| 能画远超一个方块吗 | 能。`getRenderBoundingBox` **只喂视锥剔除、不裁三角片**；但**必须自己 override**，否则控制器一出视锥整台机器消失（默认只有方块±1） | `LevelRenderer.java:1267/1296`、`MetaMachineBlockEntity.java:313-324`、参考 `FusionRingRender.java:110-112` |
| `shouldRenderOffScreen` 是"无视视锥"吗 | **不是**（与直觉相反）：它唯一作用是把这个 BE 放进 `globalBlockEntities`，**渲染时照样过视锥**。含义只是"不随 chunk 可见性走" | `ChunkRenderDispatcher.java:669-677`、`LevelRenderer.java:1296` |
| 光照怎么带 | 传进来的 `packedLight` **只对控制器那一格有效**，大模型必须**逐顶点自己采样** `LevelRenderer.getLightColor(level, pos)` 再 `.uv2(...)`，且 RenderType 必须带 LIGHTMAP；**顶点调用顺序不能改**（`vertex→color→uv→overlayCoords→uv2→normal`） | `BlockEntityRenderDispatcher.java:80`、`LevelRenderer.java:3045/3049`、`RenderUtil.java:147-163` 注释 |
| 静态大网格怎么写 | GTM 里有**可直接照抄的成品**：`MultiblockInWorldPreviewRenderer`（整结构烘进 `VertexBuffer[]`，每帧 `bind + drawWithShader`） | `MultiblockInWorldPreviewRenderer.java:76/374-406/299-368` |
| **GUI 里 3D 预览有没有现成的** | **有，而且是整套**：`SceneWidget`(+`WorldSceneRenderer`) 提供相机/拖拽/缩放/正交；**覆写 `renderBeforeBatchEnd` 就能把任意模型塞进场景**（此时 GL modelview 已是相机矩阵，用单位 `PoseStack` 画 = 世界空间）；`TransformGizmo` 带 X/Y/Z 轴与 ring 碰撞体；`ConfigPanel` + `@Configurable` **自动生成属性面板**；`Editor/MainPanel/ToolPanel` 是整套编辑器骨架 | `SceneWidget`、`WorldSceneRenderer.setBeforeBatchEnd`、`TransformGizmo`、`ConfigPanel`、`ConfiguratorParser` |
| 有没有时间轴控件 | **没有**（`Timeline`/`ListWidget`/`GroupBox` 均不存在）⇒ 时间轴自建，底座用 `gui.animation.Animation` + `AnimationFrame` + `utils.interpolate.{Interpolator, Eases}` | LDLib 控件清单 |
| ⚠️ 预览的坑 | `SceneWidget.useCacheBuffer(boolean)` 的参数是 `autoReleased`、**不是开关**（内部无条件 `useCache = true`）⇒ **有旋转部件就绝不能调它**，否则动态几何被烘死 | 源码推断（1.0.50 sources 本机缺失，见 10.2） |
| **Screen 开着时能信 `KeyMapping.isDown()` 吗** | **不能，读到的是过期值**：`KeyboardHandler.keyPress` 里 `screen.keyPressed(...)` 一旦返回 `true` 就**直接 `return`**，后面那段 `KeyMapping.set(...)` 根本不执行；而且它外层还套着 `if (minecraft.screen == null)`。⇒ 编辑器内读按键/修饰键**一律走 GLFW**（`InputConstants.isKeyDown(window, key)`，与飞行轮询同一口径）；`KeyMapping` 只用来"让玩家能改键"（读 `mapping.key.value` 拿绑定） | Forge 1.20.1-47.4.20 反编译源码 `net/minecraft/client/KeyboardHandler.java`（`keyPress` 内这两处分支） |
| 本仓现状 | `src` 里**完全没有渲染器代码**（`BakedModel`/`getModelManager`/`IRenderer` 零命中），只有 `StructureOverlayRenderer` 与 `ClientProxy` ⇒ 这套基建**从零搭**；GTCEu 1.4.4 时代的 `IControllerRenderer` 在 7.5.3 **已不存在**，对应物是 `IControllerModelRenderer`（只能出 quads）与 `DynamicRender`（才能进 BER） | 本仓 grep + 对比 |

### 10.2 仍然未知

- [ ] LDLib 1.0.50 的 **sources 本机没有**（只有 1.0.29）⇒ `useCacheBuffer` 那个坑属"源码推断"，实机前需复核。
- [ ] `Transforms` 对**嵌套子部件名**（`父/子`）的匹配行为需实机确认。
- [ ] "给其它部件传零缩放矩阵等效隐藏"是**推测，未实测**（要"只画某部件"更稳的做法是**按组拆多个 .obj**）。
- [ ] **中望 3D 子集范围最终确认**（默认按 **A** 做，B/C 记录在案）。
- [ ] 世界内 gizmo 仍**全自研**（LDLib 的 `TransformGizmo` 是 GUI 场景用的，可借它的拾取/拖拽算法，但不能直接用）。

### 10.3 由此修正的落地路径（一句话）

```
assets/gtetcore/models/obj/clock.json (forge:obj)
  → ObjLoader.INSTANCE.loadModel(ModelSettings)
  → bakeRenderable(StandaloneGeometryBakingContext.create(...)) 得 CompositeRenderable
  → 注册 DynamicRenderType + .model(...andThen { addDynamicRenderer })
  → DynamicRender.render 里 moveToFace/rotateToFace 后用
     Transforms.of(mapOf("hand_hour" to …, "hand_minute" to …)) 独立转指针
  → 静态大件走 VertexBuffer(Usage.STATIC) + drawWithShader（照抄 MultiblockInWorldPreviewRenderer）
  → 编辑器预览复用 LDLib SceneWidget + renderBeforeBatchEnd（**绝不调 useCacheBuffer**）
    + ConfigPanel/@Configurable 做参数面板
```
